# О!знаю (трек «О!дин шаг до идеального отеля»)

Проект команды vaibovovka на Ostrovok Hackathon 2026. Запуск локально: `docker compose up --build`.

Гость пишет пожелание обычным текстом — например, «тихий номер с видом на закат недалеко от моря». Система подбирает номера и по каждому условию показывает «Подходит», «Нужно уточнить» или «Не подходит», а также откуда это известно. Мы знаем об отелях то, чего нет в карточке: считаем по геоданным, спрашиваем отельера, собираем из открытых источников и карт. У каждого факта есть паспорт: источник, способ получения, дата, уверенность.

![Проверка условий в карточке отеля](docs/img/card.png)

Города: Москва и Большой Сочи — полная глубина; ещё 6 городов — автоматический слой.

**Что система знает об отеле и номере**

- **Окна номера (по фасадам и этажам корпусов):** Сочи — вид на море и горы, закат на даты поездки, часы прямого солнца в окне утром, днём и после обеда; Москва — закат на даты поездки, часы солнца и вид на Москва-Сити. Учтены рельеф Copernicus и высоты соседних зданий (OSM, спутниковые 3D-GloBFP). Это один общий расчёт видимости — см. «Механизмы» в [docs/data_and_methods.md](docs/data_and_methods.md).
- **Вокруг отеля (все отели Москвы и Сочи):**
  - шум от дорог, железной дороги и баров;
  - доля зелени, климат месяца за 30 лет;
  - пешком до пляжа, центра, остановки, детской площадки; покрытие ближайшего пляжа (Сочи);
  - подъёмы и лестницы по пути;
  - стройка рядом — по стройкам на карте OSM, оценкой;
  - район: в Сочи — Адлер, Сириус, Красная Поляна…; в Москве — районы и округа.
- **Места рядом на запросе:** любые категории («итальянский ресторан», «парк», «коворкинг», «выгул собак»), а еда, аптека, супермаркет и ветклиника — ещё и открытые в нужный час по часам работы OSM.
- **Здание:** этажность, год постройки по OSM, охранный статус по реестру объектов наследия.
- **Сам отель и номер** — со страницы Островка, как заявление отеля:
  - лифт, своя парковка, круглосуточная стойка;
  - бассейн, спа, фитнес;
  - балкон, кондиционер, кровати, кухня, питомцы.
- **На запросе:**
  - прогноз на день заезда — осадки, воздух, волны (Open-Meteo);
  - время на общественном транспорте — 2ГИС, нужен ключ.
- **От отельера:** то, чего нет в открытых данных (тишина в номере, затемнение, стол, где окна категорий) — см. «Вопросы отелю» ниже.
- **Команда:** покрытие характеристик по городу, разногласия с Островком, свежесть данных, журнал «что спрашивают, а мы не знаем», новая характеристика текстом, очередь ручной проверки.

Где данных нет, система не угадывает: «Нужно уточнить» и точный вопрос отелю. Оценки ранжируют выдачу, но обязательное условие не закрывают.

**Откуда данные и как считаем — [docs/data_and_methods.md](docs/data_and_methods.md)** (раздел «Механизмы»: закат и вид на море — примеры одного расчёта видимости из окна, который считает вид на любую цель — солнце, башню, горы, парк): источники и лицензии, паспорт факта, метод по каждой характеристике, что делает модель (только разбор текста и порядок слов в объяснении — фактов и чисел она не создаёт) и как всё проверить самим.

## Чем проект силён

- **Честность вместо угадывания.** Три ответа по каждому условию: «Подходит», «Нужно уточнить», «Не подходит». «Нет» система говорит, только если это доказано. Где данных нет, она не говорит «нет», а превращает пробел в точный вопрос отелю. Оценки ранжируют выдачу, но обязательное условие не закрывают.
- **Паспорт у каждого факта (3,6 млн фактов).** Источник со ссылкой на объект (OSM, страница Островка, Wikidata), рецепт, версия алгоритма, дата, уверенность, срок обновления. Модель фактов не создаёт: она только понимает запрос, раскладывает ответы отелей и формулирует объяснение по нашим фактам.
- **Вид из окна — интервальный расчёт лучей, а не догадка.**
  - Считается по каждой стене корпуса и каждому этажу: рельеф Copernicus, высоты соседних домов (OSM и спутниковые 3D-GloBFP), деревья, кривизна Земли.
  - «Да» — только если доказано в худшем случае всех погрешностей, «нет» — только если доказано в лучшем.
  - Одна и та же машинка отвечает про закат на даты поездки, солнце в окне, море, горы и башни Москва-Сити. Новая цель — это строка, а не новый алгоритм.
- **Отель отвечает один раз — знают все гости.** Ответ своими словами становится фактом с цитатой, выдача пересчитывается сразу. Ответ про окна категорий привязывается к стенам и этажам, и вид считается уже для конкретного номера.
- **Агент сам выбирает источник по запросу.** Даты в горизонте прогноза — прогноз Open-Meteo на день заезда, дальше — климат месяца за 30 лет. «Открыто в пятницу в час ночи» — часы работы мест на этот момент. «Доехать до X» — маршрут 2ГИС.
- **Места рядом — любые.** 52 категории словаря и любые названия мест города, расстояние и часы работы. «На карте нет» мы не выдаём за «нет».
- **Система растёт без программиста.**
  - Новая характеристика описывается текстом: черновик спецификации из готовых расчётов, пробный расчёт, включение человеком. После включения факты есть у всех отелей.
  - Журнал «Что спрашивают, а мы не знаем» показывает, что ещё нужно научиться считать.
  - Очередь ручной проверки — для случаев, где машина не уверена.
- **Город — это пакет.** Каталог Островка и открытые данные собираются в пакет с манифестом, хешами, лицензиями и аудитом. 8 городов; Москва и Большой Сочи — полная глубина, 6 907 отелей. Отель, которого не было в каталоге, добавляется по одной странице тем же конвейером (`pipeline/add_hotel.py`), без пересборки города.
- **Свежесть и противоречия видны.** У каждого факта срок годности и рецепт обновления. Расхождения ответа отеля с расчётом вынесены в отдельную панель.
- **Открыто и воспроизводимо.**
  - Код всех расчётов — в репозитории.
  - Входные данные — в `data/inputs/` и релизах (`data-raw-2026-10-29`, `data-ostrovok-2026-10-24`), со списками sha256.
  - Методы описаны в [docs/data_and_methods.md](docs/data_and_methods.md).
  - Пересчёт на тех же входах даёт те же `fact_id`.
- **Работает из России.** Модель — GigaChat-3-Ultra; без ключа модели запрос разбирается правилами.

## Вопросы отелю: ответ отеля становится знанием системы

Суть: отелю задаём вопросы только о том, чего нет ни в карточке, ни в открытых данных. Ответ отеля один раз становится фактом и дальше работает для всех гостей. Это не чат гостя с отелем.

- **Что спрашиваем.** Только пробелы, которые знает лишь отель: куда выходят окна у каждой категории номеров и на каких этажах, тишина и шумоизоляция, затемнение, рабочий стол, питомцы (масса, доплата), детская кроватка. Список задан каталогом характеристик (источник «от отеля»): у каждого отеля по одному вопросу на пробел. Своих вопросов гость не пишет. Вопрос приходит с предзаполнением — что уже сказано на странице Островка; отелю остаётся подтвердить или поправить.
- **Когда.** Вопросы ждут отеля в кабинете партнёра. Гость, у которого условие упёрлось в такой пробел («Нужно уточнить»), может отметить его кнопкой «Спросить отель». Это отметка уже существующего вопроса, а не новое сообщение: сколько бы гостей ни нажали, вопрос у отеля один.
- **Ответ — своими словами.** Например, «окна на юго-запад, с 9 по 15 этаж» или «собак до 10 кг пускаем, доплата 500 ₽». Модель раскладывает текст по полям вопроса, у каждого поля — цитата из ответа; чего в тексте нет, она не додумывает.
- **Ответ становится фактом** — с паспортом «со слов отеля», датой и цитатой.
  - Поиск ставит по нему «Подходит» или «Не подходит» для всех следующих гостей.
  - Объяснение для гостя цитирует отель: «Можно с животным: да — пускают собак и кошек, ответ отеля».
  - Ответ о размещении номеров привязывается к стенам и этажам корпуса. Закат или вид из окна считаются уже для конкретной категории номера.
- **Сверка.** Ответ отеля, который расходится с расчётом (отель пишет «вид на море», а луч из окна упирается в соседний дом), попадает в панель «Противоречия фактов». В песочнице кабинета отвечает имитатор: такие ответы помечены «ответ имитатора» и настоящий ответ отеля не заменяют.

Следующий шаг — порядок вопросов в кабинете по спросу: первыми те пробелы, в которые чаще всего упираются запросы гостей.

## Быстрый старт

```bash
git clone https://github.com/clavasyp/oznayu-ostrovok-hackathon.git
cd oznayu-ostrovok-hackathon
cp .env.example .env
docker compose up --build
```

Открыть http://localhost:8080. Миграции и загрузка данных идут сами (сервис `init`), других команд не нужно. Нужны Docker с Compose v2 и интернет для первой сборки: Docker Hub, GHCR, PyPI, npm.

## Что поднимается

| Сервис | Что делает | Когда готов |
|---|---|---|
| `db` | PostgreSQL 16 + PostGIS 3.6 (`postgis/postgis:16-3.6`), данные в томе `pgdata` | `pg_isready` по TCP |
| `init` | Миграции Alembic и загрузка пакетов городов из `packs/`; уже загруженный пакет повторно не грузится | завершился с кодом 0 |
| `app` | API и интерфейс на порту 8080 | `/health` → `{"status":"ok"}` |

Образ приложения один на `init` и `app`, сборка в три стадии (`Dockerfile`): интерфейс (Node 24) → зависимости Python строго по `uv.lock` → итоговый образ без инструментов сборки, процесс не от root. Версии образов зафиксированы. Все сервисы — `linux/amd64`, на Apple Silicon Docker Desktop запускает их через эмуляцию.

## Маршруты

| Путь | Что |
|---|---|
| `/` | Интерфейс. Пока он не собран — страница со ссылками на API |
| `/health` | Готовность: `{"status":"ok"}`; пока идёт запуск — 503 и фаза |
| `/live`, `/ready` | Процесс жив; то же, что `/health` |
| `/docs` | Все маршруты API (OpenAPI) |
| `/api/...` | Города и покрытие, отели и факты, поиск, вопросы отельеру, противоречия |

Входа нет: кабинет отельера и админка открыты, тестовые учётные данные не нужны.

## Что попробовать

1. **Поиск текстом с доказательствами.** Город «Большой Сочи», запрос «тихий номер с видом на закат недалеко от моря, 15 ноября». Закат посчитан по окнам: этаж и сторона каждого фасада, рельеф, высоты соседних зданий. В объяснении видно, например, «окна на юго-запад, этажи 7–14, подходят не все окна». Где номер, знает только отель, поэтому статус «Нужно уточнить», а вопрос отельеру уходит одной кнопкой.
2. **Агент добывает то, чего нет в каталоге.** Запрос «обязательно рядом итальянский ресторан». Такой характеристики в каталоге нет, но система берёт категорию места и считает расстояние по местам города на запросе. «Подходит» — с названием места и расстоянием. «Нет» система не говорит, ведь места на картах отмечены не все: такие отели получают «Нужно уточнить». Слова о качестве («хорошие», «вкусные») честно остаются «неизвестно» — рейтингов у нас нет.
3. **Диалог с отельером.** Radisson Collection Парадиз, запрос «обязательно можно с собакой». Сначала «Нужно уточнить». Ответ в кабинете отельера (песочница отвечает за имитатора) раскладывается по полям, и выдача пересчитывается: «Подходит». Ответ о размещении номеров (вкладка «Где окна номеров», например Grand Karat: «окна на юго-запад, с 9 по 15 этаж. Других вариантов нет.») становится этажами и стенами корпуса. С датой 15 ноября закат из окна переходит из «Нужно уточнить» в «Подходит».
4. **Новая характеристика текстом.** Панель команды → «Новая характеристика»: «сколько кафе в 500 м». Дальше черновик спецификации, проверка, пробный расчёт и «Включить». Характеристика считается для всех отелей Москвы и Сочи, факты с паспортом попадают в базу. Поиск сразу понимает её в запросе «много кафе». Код не меняется. То же можно начать из журнала «Что спрашивают, а мы не знаем» кнопкой «Сделать характеристику».
5. **Удобства отеля и районы.** «Отель в Адлере у моря с бассейном, своя парковка обязательна». Район — фильтр выдачи («Из запроса: только Адлер»); в Москве так же — районы и округа по границам OSM: «в Хамовниках», «не в ЦАО», «в Новой Москве». Бассейн и парковка — со страницы отеля на Островке, как заявление отеля: «С бассейном: да (Островок: «Открытый бассейн»)». «Парковка отсутствует» на странице даёт «Не подходит».
6. **Погода и климат — агент выбирает источник по датам.** «Приеду <дата через 3 дня>: чтобы не было дождя, чистый воздух и спокойное море» — прогноз Open-Meteo на день заезда прямо на запросе (осадки, PM2.5, высота волн). «В июле тепло и без дождей» — климат месяца за 30 лет (ERA5) по каждому отелю.
7. **Место, открытое в нужный час.** «В пятницу в час ночи обязательно должна быть открыта еда рядом» — места города с часами работы OSM: «да («Вкусно — и точка», 249 м, открыто: Mo-Su 05:00-03:00)». Нет часов — «уточним», а не «нет».
8. **Сравнение.** На карточках отметьте 2–3 отеля → «Сравнить»: условия запроса бок о бок, у каждого — вердикт и причина.
9. **Актуализация.** Панель команды → «Свежесть данных»: у каждого значения дата и срок обновления, у каждого рецепта — чем обновлять. Поставьте дату через год — видно, что устареет (страницы Островка — через 30 дней, расчёты — через полгода). Ответ по устаревшему факту остаётся, но помечен «данные пора обновить».
10. **Здание и тип жилья.** Москва: «хостел в историческом здании», «пятизвёздочный отель в памятнике архитектуры». Тип жилья и звёзды — фильтр по странице Островка; охранный статус — объект наследия в контуре корпуса (Wikidata, номер реестра в паспорте); «старинное здание» — год постройки по OSM, оценкой.
11. **Солнце и горы из окна (Сочи).** «Поменьше утреннего солнца в июле и вид на горы» — по фасадам: где расчёт доказывает «да», там «да»; где соседние дома могут закрыть — «по оценке». Москва: «в Тропарёво с видом на закат» — «окна на запад, этажи 18–23» (закат по всей Москве без района — около 30 с на Mac, где база в эмуляции).
12. **Вопрос отелю из карточки.** У пункта «нужно уточнить» в карточке отеля — «Спросить отель»: вопрос с предзаполнением уходит в кабинет отельера; про окна номеров — «Спросить отель, где окна номеров» открывает кабинет на вкладке «Где окна номеров». Ответ своими словами → статус отеля пересчитывается («Нужно уточнить → Подходит»).
13. **Доехать до места (Москва).** «Доехать до Большого театра и рядом итальянский ресторан» — цель находится среди мест города; с ключом 2ГИС для первых отелей страницы — время в пути («пешком 4 мин, 2ГИС»), без ключа — оценка по прямой.
14. **Ручная проверка командой.** Панель команды → «На проверку»: отели, у которых машина не уверена в здании, и возможные дубли объявлений. Кандидаты с доказательствами (адрес на карте, совпадение дома и улицы, точка отеля в контуре), решение «это здание / ни одно / не уверен» записывается с именем и временем.
15. **Вид на Москва-Сити.** Москва: «отель с видом на Москва-Сити» — первым Palmira Art: «по расчёту — окна на юг, этажи 16–23». Тот же расчёт лучей, что у заката, только цель — башни Сити из OSM (выше 150 м). «Видно» — не шпиль, а не меньше 50 м башни; в паспорте — какая башня и сколько метров видно. «Пальмиры» не было в снимке Островка: её добавили по одной странице (`pipeline/add_hotel.py`) тем же конвейером, что весь город.

## Зависимости и ресурсы

Рекомендованные ресурсы: **8 ядер CPU, 16 ГБ RAM, в Docker Desktop — от 8 ГБ памяти, 20 ГБ свободного места на диске**. Минимум — 4 ядра и 6 ГБ памяти Docker: работает, но первый запуск дольше. Место (замер 29.10): база после загрузки — 8,2 ГБ (3,6 млн фактов с индексами), образы — 1,8 ГБ (приложение 0,9 ГБ, PostGIS 1 ГБ), плюс кеш сборки. Первый запуск — загрузка 8 городов в пустую базу: на Mac с Apple Silicon 7–12 минут (замер — 405 с при свободной памяти), потому что PostGIS и приложение там работают как `linux/amd64` в эмуляции. На ноутбуке с Intel или AMD эмуляции нет. Повторный запуск с той же базой — секунды: загруженный пакет не грузится заново.

Зависимости — только Docker с Compose v2:
- PostgreSQL 16 + PostGIS 3.6 — сервис `db` (`postgis/postgis:16-3.6`);
- приложение FastAPI + интерфейс React — сервис `app` (образ собирается из `Dockerfile`), миграции и данные — сервис `init` (тот же образ);
- LLM — GigaChat (`GigaChat-3-Ultra`, API в формате OpenAI chat/completions), необязательно: без ключа работает разбор правилами;
- 2ГИС — необязательно, время на транспорте на запросе.

## Переменные окружения

Все — в `.env.example`. Без `.env` compose берёт те же значения по умолчанию. Секреты — только в `.env`, он не попадает ни в git, ни в образ.

| Переменная | По умолчанию | Что |
|---|---|---|
| `DATA_MODE` | `db` | `db` — база, куда `init` загрузил пакеты городов; `fixtures` — заглушки из фактов v9 без базы (для интерфейса без Docker) |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `oznayu` | База; адрес для `init` и `app` compose собирает из них |
| `LLM_PROVIDER` | `gigachat` | LLM-шлюз: `gigachat`; `openai_compat` — любой OpenAI-совместимый API; `anthropic` — родной API Anthropic |
| `LLM_MODEL` | `GigaChat-3-Ultra` | Модель |
| `LLM_API_KEY` | пусто | Ключ LLM (у GigaChat — ключ авторизации из личного кабинета) |
| `LLM_BASE_URL` | `https://api.giga.chat/v1` | Адрес API |
| `GIGACHAT_SCOPE` | `GIGACHAT_API_PERS` | Тип ключа GigaChat: физлицо или организация (`GIGACHAT_API_B2B`, `GIGACHAT_API_CORP`) |
| `TWOGIS_API_KEY` | пусто | Ключ 2ГИС для времени на транспорте на запросе (необязательно) |
| `DATABASE_URL`, `PACKS_DIR` | см. `.env.example` | Только для запуска вне Docker |
| `WARMUP` | `1` | После загрузки пакетов прогреть кеш базы запросами показа в фоне — первый поиск быстрее |

**Ключ модели.** Модель только разбирает запрос, раскладывает ответы отельера и пишет объяснения по нашим фактам; фактов она не придумывает. Без ключа всё работает на правилах, интерфейс помечает офлайн-режим. По умолчанию — GigaChat (`LLM_PROVIDER=gigachat`, модель `GigaChat-3-Ultra`, адрес `https://api.giga.chat/v1`): он работает из России. Достаточно `LLM_API_KEY=<ключ авторизации GigaChat>`, токен на 30 минут шлюз получает сам; сертификат Минцифры для `api.giga.chat` лежит в репозитории (`agents/llm/certs/`). Любой OpenAI-совместимый API — `LLM_PROVIDER=openai_compat` со своими `LLM_BASE_URL` и `LLM_MODEL` (например, Claude: `https://api.anthropic.com/v1/`, `claude-opus-5-5` — из России недоступен). Проверено 29.10 на эталоне из 61 запроса в режиме «правила + модель»: GigaChat-3-Ultra — обязательные условия точно в 58 из 61 (в трёх запросах — лишнее или неверно понятое условие), Claude Opus 5.5 — в 61 из 61; разбор запроса на стенде — около 6 с.

**Ключ 2ГИС (необязательно).** С `TWOGIS_API_KEY` время на общественном транспорте («из аэропорта без пересадок», «есть ночной транспорт») считается по 2ГИС на запросе — для первых 10 отелей страницы, не больше 300 запросов в месяц. Без ключа пункт честно остаётся «нужно уточнить».

## Данные и сидирование

Сидирование автоматическое. При каждом запуске `init` применяет миграции и грузит пакеты городов из `packs/` (формат — `packs/FORMAT.md`), сверяя хеши из `manifest.json`; строки идут потоковым `COPY`, `init` печатает прогресс по видам файлов. Вручную — `make seed` или `docker compose run --rm init`. Тяжёлые расчёты делаются заранее: в пакетах только результаты. Уже загруженный пакет повторно не грузится (повторный `init` — около секунды).

Время загрузки (29.10): холодный запуск `docker compose up --build` с удалённой базой — 405 с до ответа `/health` (образ из кеша сборки); `init` на чистой базе — 375 с на все 8 городов (Москва 228 с, Сочи 83 с, индексы фактов после данных — 46 с; Mac с Apple Silicon, PostGIS в Docker в эмуляции amd64). Плюс сборка образа при первом `docker compose up --build`.

Сейчас в `packs/` — 8 городов, 7206 отелей, 3 605 737 фактов с паспортом (Москва — 2 816 326, Сочи — 765 494):

- **Москва и Большой Сочи — полная глубина:** полный каталог Островка (снимок 24.10, `pipeline.build_packs`; категории шести отелей показа — снимок 27.10, `pipeline.supplement_categories`): 4211 и 2695 отелей, 22 011 категорий номеров. Георасчёты по всему каталогу, корпуса и фасады, места рядом и станции, очередь ручной проверки.
- **Ещё 6 городов — автоматический слой из расчётов v9:** по 50 отелей.
- Вопросы отельеру с предзаполнением — у каждого отеля Москвы и Сочи (вне когорты v9 — по шаблонам v9, предзаполнение — заявления страницы Островка), покрытие по 54 характеристикам, сверка с карточкой Островка.

Пересборка:

- шесть автоматических городов — `python -m pipeline.build_v9_packs --city spb --city kazan …` (сборщик v9 не перезаписывает пакет другой сборки);
- Москва и Сочи — цепочка `build_v9_packs --out /tmp/v9` → `build_packs --v9-packs /tmp/v9` → `calculate_city` / `calculate_moscow` → `finalize_packs` → `supplement_categories` → `publish_packs` (нужны профиль `builder` и исходники: снимки Островка из релизов данных, срезы OSM, растры; команды — `connectors/README.md`);
- после пересборки — `make audit` (офлайн-аудит пакетов, отчёт в `pipeline/reports/`) и `make test-packs` (поставляемые пакеты в настоящей PostGIS).

Без Docker API может работать на заглушках из тех же фактов v9 (`app/fixtures/`, `DATA_MODE=fixtures`).

## Разработка

```bash
uv sync --extra api --extra llm                          # окружение приложения; группа dev ставится сама
uv sync --all-extras                                     # + сборка пакетов городов (Сева, Лера, лид)
DATA_MODE=fixtures uv run uvicorn app.main:app --port 8080  # API на заглушках, без базы
make db                                                  # база на 127.0.0.1:55432, адрес — DATABASE_URL в .env
uv run --env-file .env python -m pipeline.init           # миграции и пакеты в эту базу
uv run --env-file .env uvicorn app.main:app --port 8080  # API на этой базе
uv run python -m pipeline.build_v9_packs --city kazan    # пересобрать автоматический город из v9
make test && make lint
make test-db                                             # + тесты на настоящем PostGIS (база oznayu_test)
```

Версии зафиксированы в `uv.lock`. После правки `pyproject.toml` — `uv lock` и закоммитить lock-файл. CI проверяет это сам.

**CI** (`.github/workflows/ci.yml`) на каждый PR и в `main`:
- `uv lock --check`, ruff и pytest;
- `docker compose up --build` с замером времени до `/health`;
- проверка `/` и `/api/cities`, повторный запуск `init`.

Контракты (факт, плагин, запрос, API, пакет города) — `docs/design/contracts.md`.
