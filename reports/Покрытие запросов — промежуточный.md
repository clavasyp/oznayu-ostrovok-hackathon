[вывод] Главная находка — нельзя считать знакомое слово покрытым условием. ### Выводы

[вывод] Для следующих этапов важны параметрические семейства: место/кухня/режим, маршрут к любой цели с mode/time, поездка туда-обратно с последним возвращением, доступная прогулочная среда, субъективное качество с доказательствами. Это не означает заново заводить W03. Базовый «бассейн», звёзды, цена за ночь и состав гостей должны попадать в `base_catalog`/`query_parameter`; глубина детского бассейна, реальные гарантии категории, диета и совместимость с ограничениями — отдельные вопросы.

[вывод] Для низких процентов нет основания писать «система покрывает только 7,3% спроса»: измерены отношения предикатов к узкому v3, а не качество всего продукта. Доля полностью помещающихся в 80 текстов также занижена самим составом панели — отзывы перечисляют сервис, бытовые детали и впечатления, а вопросы SE включают разрешение проблем. Практическое следствие — поддержать видимость unmatched и приоритизировать новые семейства, а не показывать общий маркетинговый процент.

[вывод] «Вкусно», «уютно», «тихо», «безопасно» сохраняются с исходным субъектом/датой и не меняются на измеряемый суррогат. Для жёсткого условия без доказательства ответ `unknown` или уточнение; оценка/агрегат мнений может быть отдельной осью с бейджем (D18), но не закрывает предикат автоматически.

### Пробелы

- Whole-query data coverage не вычислялось: для каждого кандидата нужно связать **каждый** атом с тем же объектом/датой/целью/входом/размещением и проверить все обязательные ветви. V9 сохраняет данные для этого, но наличие ID и строки факта недостаточно.
- Непрерывный доступный маршрут не доказан отсутствием тега ступеней; perceived quiet не равен N01/N05; разрешение готовить своей плитой не равно M03; общий чайник не равен M04; adjoining не гарантирует F04 connecting; именованное здание/мост не автоматически V03 «памятник»: МИД и Golden Gate оставлены partial без нового требования официального реестра; ширина душа не равна A04 порог / A05 дверь.
- Количественные параметры, условия гарантированного назначения и субъективная формулировка иногда остаются неоднозначны. `partial` не превращается в `exact` ради красивого показателя.
- Из остальных шести городов не снимались новые факты и не менялись V9; их 72 старых отзыва используются только для таксономии.

## 3. Как это проверить воспроизводимо, не смешав лицензии и смысл?

### Главное

[вывод] Команде переданы 200 переносимых авторских тестов структуры и отдельный внутренний набор настоящих источников. Это разработческий eval и аннотации Codex, а не человеческий gold и не измеренная точность LLM.

### Подтверждённые результаты

- [факт] `eval/queries.jsonl` по умолчанию содержит **200 авторских synthetic**: 80 контрактов каталога и 120 парных AND / OR / desirable / negation случаев. Во всех есть expected atoms и honest answer type; OR не превращается в AND, желательный предикат не становится обязательным, unmatched не исчезает.
- [факт] `eval/internal_reviewed_references.jsonl` содержит **104 настоящих семантически reviewed источника** (90 OST + 14 SE) с локальными pointer, SHA и expected atoms. `load_eval.py --mode internal-reviewed` реально восстанавливает исходные тексты и проверяет SHA, без HTTP. Это необходимое дополнение к synthetic.

### Выводы

[вывод] Оценка дальнейшей работы для планирования, **не измерение труда людей**: независимая смысловая проверка 100 коротких/средних текстов может потребовать порядка 2–6 человеко-часов; проверка спорных атомов с параметрами и all/some гарантией увеличивает стоимость. Диапазон — проектная гипотеза, не нормирование производительности. Ручные часы добычи Москвы/Сочи по местам/маршрутам оцениваются городскими ветками по своим реальным действиям; из времени выполнения этого скрипта их выводить нельзя.

[вывод] Контракт для следующего этапа AST: `original_span + atom_id + semantic_predicate + requiredness + scope/parameters + logic_group + mapping_layer + mapping_status + fact_evaluation`. У atom есть список недостающего смысла и evidence; сохранённый partial не считается выполнением одной половиной. Человек должен видеть исходный фрагмент и исходный источник рядом с предложенным уточнением.

### Пробелы

- Рабочий production parser/recommender на наборе ещё не запускался; независимой human-gold оценки и accuracy нет.
- 200 synthetic гарантируют ширину контрактов и ловушки структуры, но не заменяют будущие реальные поисковые логи. 104 reviewed настоящих источника тоже не являются логами бронирования.
- Внешний NC слой нельзя автоматически включать в коммерческий продукт; разрешение на сбор Островка не равно свободной лицензии текста; CC BY-SA материалы требуют своей атрибуции/условий. Default portable экспорт поэтому содержит только авторские случаи.
- Обновление `docs/`, каталога 80 и production `tests/` в этой ветке не выполнялось: здесь подготовлены проверяемые материалы для следующих этапов V11.

Не больше семи предложений команде:

1. Считать спрос в четырёх отдельных стратах; для публичных вопросов явно показывать, что это lodging-help, а не обязательно подбор.
2. Принять разделение базовых полей, параметров поиска, дополнительных контрактов и outside; nightly price не M06.
3. Утвердить сохранение всех атомов и unmatched с разными осями смысла и факта, включая область отрицания/OR.
4. Приоритизировать POI type/cuisine/time, маршруты из отеля к цели и возвращение; W03 использовать повторно для пешего режима.
5. Субъективное хранить как мнение/агрегат с provenance и датой; качество комнаты и гарантии спрашивать у отельера либо проверять человеком.
6. Использовать 200 авторских структурных случаев плюс отдельные 104 reviewed настоящих источника; не объявлять их независимым gold.
7. После появления реального потока запросов строить новый временной holdout, измерять query-level ответы с каждым обязательным атомом и отдельно actual data coverage.
