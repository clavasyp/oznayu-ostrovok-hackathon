## Пилот импорта Островка (этапы 1–2 Севы)

`ostrovok_site.py` читает готовый снимок, не обращаясь к сайту. Вход — папка
`snapshot_2026-10-24/` с `manifests/pages.jsonl` и `next/<xx>/*.json.gz` из релиза
`data-ostrovok-2026-10-24`. Папка снимка и результат пилота — вне репозитория.
Точные контракты и этапы — в конце `docs/tasks/seva.md`.

```bash
uv sync --extra api
uv run python -m pipeline.import_ostrovok \
  --snapshot /absolute/path/snapshot_2026-10-24 \
  --out /tmp/ostrovok-pilot --limit-per-city 5
```

Если `.venv` уже подготовлена, вместо `uv run python` можно использовать
`.venv/bin/python`; для тестов — `.venv/bin/pytest`. Новых зависимостей коннектор не добавляет.

По умолчанию обрабатываются оба города. Для одного — `--city moscow` или `--city sochi`.
Выход должен быть новым или пустым каталогом; штатные `packs/` защищены от перезаписи.
В выходе — `moscow/manifest.json`, `sochi/manifest.json` и `data/{hotels,room_types,facts}.jsonl.gz`.
`import_report.json` содержит количества и исключённые записи с причинами.
Повторение на тех же входах в другом выходном каталоге даёт те же байты и хеши.

Пилот ограничен выборкой, **не проверяет границы/подзоны** и не объединяет данные с v9.
Файлы нельзя использовать вместо полных рабочих пакетов. Редирект на выдачу, отсутствие
`__NEXT_DATA__`, неправильная структура или ID — исключение с причиной, а не «отель закрыт».
Неизвестные поля D26 не превращаются в отрицательные факты.

Теги оборудования и текст кроватей — частичные заявления категории, с
`hard_condition_eligible=false`. Они не доказывают размеры, скорость Wi-Fi, вид,
приватность балкона или полноту вариантов. Источники содержат относительный файл снимка,
JSON pointer, дату публикации снимка, хеш несжатого JSON и отдельно заявленный HTML-хеш.

### Загрузка в отдельную тестовую PostGIS

Нужна **отдельная база с именем, заканчивающимся на `_test`**. Загрузчик заменяет данные
города, поэтому использовать здесь основную базу разработки нельзя. Применить к тестовой
базе штатные миграции, затем добавить `--load-test-db` к команде сборки:

```bash
# TEST_DATABASE_URL задаётся локально; не добавлять пароль в git.
DATABASE_URL="$TEST_DATABASE_URL" uv run alembic upgrade head
uv run python -m pipeline.import_ostrovok \
  --snapshot /absolute/path/snapshot_2026-10-24 \
  --out /tmp/ostrovok-pilot-db --limit-per-city 5 --load-test-db
```

Без `--load-test-db` соединения с БД нет. С этим флагом используется `TEST_DATABASE_URL`,
проверяется суффикс имени БД и вызывается существующий `pipeline.load_packs.load_pack`.
Повторную загрузку уже собранного результата можно проверить без пересборки:

```bash
uv run python -c 'import os; from pathlib import Path; from pipeline.import_ostrovok import load_test_database; print(load_test_database(Path("/tmp/ostrovok-pilot-db"), os.environ["TEST_DATABASE_URL"]))'
```

Проверки коннектора и сборки: `uv run pytest -q tests/test_ostrovok_import.py`.
Интеграция с БД включается через `TEST_DATABASE_URL`; без него этот тест явно пропускается.

## Полный каталог, OSM и расчёт Сочи (этапы 3–6)

Реализация: `city_geography.py`, `osm_pbf.py`, `pipeline/build_packs.py`,
`calculators/route_graph.py`, `calculators/poi_hours.py`, `calculators/route_geo.py`,
`pipeline/calculate_city.py`. Нужен профиль `uv sync --all-extras`.

Исходники и результаты находятся **вне репозитория**. Для выполненного прогона это
`/private/tmp/seva-data/`; временная папка может очищаться системой. Полный снимок
`snapshot_2026-10-24/` взят из того же релиза, проверены SHA-256 обоих архивов index/next.
HTML для этих этапов не нужен. Сводный проверочный отчёт сохранён в репозитории:
`pipeline/reports/seva_stages_3_6.json`.

### Источники географии

- Москва: [Geofabrik, Central Federal District](https://download.geofabrik.de/russia/central-fed-district.html),
  файл `central-fed-district-261022.osm.pbf`.
- Сочи: [Geofabrik, South Federal District](https://download.geofabrik.de/russia/south-fed-district.html),
  файл `south-fed-district-261022.osm.pbf`. Действительное имя — `south`, не `southern`.
- Зафиксирована дата 22.10.2026 для сравнения с v9, проверены контрольные суммы Geofabrik.
- Москва — административный `relation/102269` (включая Новую Москву),
  [справочник OSM](https://wiki.openstreetmap.org/wiki/RU:Москва/Административно-территориальное_деление).
  Большой Сочи по D28 — объединение `relation/365233` и `relation/11865346` (Сириус).
  Полигоны собраны непосредственно из этих PBF, граница включается в отбор.
- Подзоны — именованные полигоны OSM, Сириус имеет приоритет над Адлером. Остаток —
  `other_greater_sochi`; название в URL не определяет границы и подзону. В пакете `subzone` —
  название для гостя («Адлер», «Сочи (центр)», остаток — «Большой Сочи»), код — `subzone_id`.
- Подъём — только оценка DSM Copernicus GLO-30. Оба использованных тайла имеют те же
  SHA-256, что в v9. DSM не выдаётся за профиль поверхности дороги или доступность.

### Как повторить

Ниже команды из корня проекта. Пути исходников можно заменить своими. Выход сборщика
пакетов должен быть новым/пустым. Срез OSM при повторном запуске проверяет свои хеши.

```bash
.venv/bin/python -m connectors.osm_pbf \
  --pbf /private/tmp/seva-data/south-fed-district-261022.osm.pbf \
  --city sochi --out /private/tmp/seva-data/osm/sochi
.venv/bin/python -m connectors.osm_pbf \
  --pbf /private/tmp/seva-data/central-fed-district-261022.osm.pbf \
  --city moscow --out /private/tmp/seva-data/osm/moscow
# Москва и Сочи в packs/ — уже полный каталог; вход build_packs — v9 в отдельной папке.
.venv/bin/python -m pipeline.build_v9_packs --out /tmp/v9
.venv/bin/python -m pipeline.build_packs \
  --snapshot /private/tmp/seva-data/snapshot_2026-10-24 --v9-packs /tmp/v9 \
  --osm-root /private/tmp/seva-data/osm --out /tmp/catalog-repeat
.venv/bin/python -m pipeline.calculate_city \
  --base-packs /tmp/catalog-repeat --osm-dir /private/tmp/seva-data/osm/sochi \
  --raster-dir /private/tmp/seva-data/raster_tiles --out /tmp/calculated-repeat
```

Для быстрой сверки без полного расчёта добавить `--control-only` к последней команде
и указать отдельный новый выход. Контроль использует исходные 89 координат, прежние
принятые связи с корпусами, bbox/фильтр первой вершины v9. **Полный расчёт использует
исправленный расширенный срез.** Несовпадение контроля останавливает полный расчёт.
Это сверка статуса и основной метрики с допуском 0,01 / относительным 1e-8,
не независимая оценка физической точности.

`RoutePoiCalculator.run(subjects, ctx)` принимает другие даты через
`ctx.params["trips"] = [{"start": "2026-10-27", "end": "2026-10-28",
"arrival_local": "2026-10-27T02:00:00"}]`. По умолчанию — две контрольные поездки v9.
Регулярные часы, праздничный календарь и местное время считаются отдельно от маршрута;
часы заведения не заменяют часы кухни. Моментальная фактическая работа не гарантируется.

### Загрузка и просмотр

Для выполненного прогона создана отдельная локальная PostgreSQL 16.15 / PostGIS 3.4.6:
`127.0.0.1:55439`, пользователь `seva`, база `seva_catalog_test`, без пароля, только localhost.
Штатный стек жюри по-прежнему задаётся `docker-compose.yml`.

Команды исторического прогона этапов 3–6 (актуальные пакеты этапа 10 — ниже):

```bash
DATABASE_URL=postgresql+psycopg://seva@127.0.0.1:55439/seva_catalog_test \
PACKS_DIR=/private/tmp/seva-data/calculated-packs .venv/bin/python -m pipeline.init
DATA_MODE=db DATABASE_URL=postgresql+psycopg://seva@127.0.0.1:55439/seva_catalog_test \
  .venv/bin/python -m uvicorn app.main:app --port 8080
```

Служба БД использует временные бинарники
`/private/tmp/seva-postgres-volume/Postgres.app/Contents/Versions/16/bin/`
и кластер `/private/tmp/seva-postgis-db`. Эти файлы не устанавливались в Applications.
После перезагрузки для повторения удобнее штатный Docker/PostGIS; временный кластер
можно запустить тем же `pg_ctl -D /private/tmp/seva-postgis-db -l ... start`, если образ
ещё подключён. Значения выше относятся только к созданной тестовой базе.

На завершении этапов 3–6 рабочие `packs/` ещё содержали v9; публикация и замер запуска
относятся к этапу 10 ниже. В `calculated-packs/` подготовлены новые Москва/Сочи и неизменённые
шесть автоматических городов. Вопросы отельеру сохранены из v9; новые вопросы относятся
к работе агента. Тяжёлые графы/растры не помещены в рабочие пакеты. Геометрия трасс и
проверка запрещённых узлов находятся в `calculated-packs/audit/` для последующей интеграции.

## Этапы 7–10: Москва, фасады, D34 и публикация

Предварительная сборка требует профиля `builder` и исходников. Приложение использует
только `api`/`llm`, готовые файлы и БД; при запуске не нужны ни ключ карт, ни граф, ни растры.

```bash
.venv/bin/python -m pipeline.calculate_moscow \
  --base-packs /private/tmp/seva-data/calculated-packs \
  --osm-dir /private/tmp/seva-data/osm/moscow \
  --raster-dir /private/tmp/seva-data/raster_tiles \
  --out /tmp/moscow-repeat
.venv/bin/python -m pipeline.finalize_packs \
  --base-packs /tmp/moscow-repeat --osm-root /private/tmp/seva-data/osm \
  --city moscow --out /tmp/moscow-ready-repeat \
  --built-at 2026-10-26T14:35:00Z
.venv/bin/python -m pipeline.finalize_packs \
  --base-packs /private/tmp/seva-data/calculated-packs \
  --osm-root /private/tmp/seva-data/osm --city sochi \
  --out /tmp/sochi-ready-repeat --built-at 2026-10-26T14:35:00Z
```

Москва использует компактные массивы узлов и общие метаданные рёбер из облегчённого
алгоритма v9. Полный граф один: район — очередь отелей, не обрезка пути. Части содержат
хеши, факты, трассы и признак завершения. Добавить `--resume` с тем же выходом можно
только при совпадении входов, параметров и исходников калькулятора. На изменённых входах
нужен новый каталог. Отсутствие маршрута в срезе не означает отсутствие реального пути.

Каталог DSM обязателен: входные TIFF включены в хеши возобновления, прогон без единой
оценки DSM не публикуется. Для текущих выбранных московских маршрутов понадобился
`Copernicus_DSM_COG_10_N55_00_E037_00_DEM.tif`, SHA-256
`027a31311fd198c54d08d7f6025835fa34b24c3e08ddc43023b485ee63f21320`, тот же, что в v9.
На первом прогоне DSM был пропущен; исправление выполнено по сохранённым трассам:

```bash
.venv/bin/python -m pipeline.complete_ascent \
  --base /private/tmp/seva-data/moscow-packs-v2 \
  --audit /private/tmp/seva-data/moscow-packs-v2/audit \
  --osm-dir /private/tmp/seva-data/osm/moscow \
  --raster-dir /private/tmp/seva-data/raster_tiles --out /tmp/moscow-dsm-repeat
```

Этот шаг применяет тот же `dsm_ascent`, сохраняет параметры поездки и трассы. Тест
сравнивает весь W04-паспорт с обычным полным расчётом на синтетическом DSM.
Исходные 142 части первого прогона сохранены; они содержат состояние до довычисления.
Текущий `calculate_moscow` уже подключает DSM сразу. В итоговые пакеты идёт исправленный
результат, а исходники PBF/DSM и граф — нет.

Принятие нового корпуса требует полного адреса (включая тип улицы, корпус, строение,
литеру, владение), точки внутри контура и единственного подходящего здания. Прежние
принятые связи v9 воспроизводятся отдельно. Неуверенные случаи дают `curation_items`,
в том числе задачу ручного поиска, когда надёжного кандидата нет. Автоматических
`curated` нет. Для канонического файла кандидатов v11 — дополнительные параметры
`--v11-candidates /path/candidates.jsonl.gz --v11-sha256 <проверенный-хеш>`.
Набор v11 отсутствует локально; отчёт о нём не выдаётся за сам набор данных.

Фасады D39 и метки мест описаны в `packs/FORMAT.md`. Категории мест берутся из
словаря Данила `agents/catalog/places.json` и из характеристик каталога, которым место
нужно (`core.geo_store.CATALOG_PLACES`: аптека L01, супермаркет L03, бар N04…); кухня не
угадывается по названию. Место без категории (скамейка, урна, парковка, сам отель) в пакет
не идёт; пары «отель → место» не хранятся — их считает запрос PostGIS (D41).
Окна, этажи, «главный корпус» и гарантии категории из геометрии не выводятся.

### 2ГИС: ключ и подключение

27.10 пользователь передал демо-ключ: он сохранён только в локальном игнорируемом
`.env` как `TWOGIS_API_KEY` (права 0600). Успешных HTTP-ответов в проверенной среде
не получено: к обоим API-хостам соединение завершалось таймаутом. curl без ключа
показал таймаут TLS-рукопожатия; скрипт проверки тогда записывал любой таймаут как
`network_timeout`, теперь такое зависание — `tls_timeout`. Валидность ключа и доступ
к продуктам пока не подтверждены.
Таблица времени метро пуста; существование OSM-станции не даёт минуты поездки.

Ключ — только в `TWOGIS_API_KEY` вне git: в окружении или в `.env` (`--env-file`,
по умолчанию `.env`). Проверка, сборщик и `python -m connectors.twogis` читают его
одинаково и только с `--execute`. Демо-ключ предназначен для проверок: локальный
предел 20 единиц на сервис в месяц (предел сервиса 1000 по D37), максимум две ячейки
и две страницы при пробном сборе. Кеш и журнал расхода — один общий каталог для обоих
городов: по умолчанию `data/twogis_cache/` в репозитории (игнорируется git, в образ
не попадает; `--cache` меняет путь). Резервирование сохраняется до запроса, включая
ошибки; попадание в кеш лимит не тратит. Кеш не зависит от ключа: сохранённые ответы
воспроизводятся без ключа и с новым ключом без повторного расхода.
Routing и public transport учитываются в одном консервативном локальном бюджете.
Это локальный учёт этого сборщика, не остаток баланса у провайдера.

```bash
# Рубрики — проверенные ID Categories API, region_id — ID региона 2ГИС, не код субъекта.
# rubrics.json: {"region_id": 32, "rubric_categories": {"<реальный ID>": ["italian"]}}
# Без --execute выводится только план, сеть не вызывается.
.venv/bin/python -m pipeline.collect_twogis \
  --pack /tmp/moscow-ready-repeat/moscow --rubrics /path/rubrics.json \
  --out /tmp/twogis-check
# После проверки доступа и рубрик для пробного сбора добавить --execute.
# Массовый сбор — только с действующей подпиской, --subscription и явным
# --monthly-unit-limit, согласованным с доступным бюджетом. Подписку код не оформляет.
# Готовый bundle присоединяется к finalize_packs через --twogis-bundle /path/twogis.json.
```

`--transit-requests` у сборщика принимает JSON-массив пар станций и параметров
Public Transport API; координаты проверяются по станциям пакета, `start_time` обязателен.
Минуты и пересадки сохраняются только из ответа на эту пару/дату/профиль. Матрица не
подменяет расписание. Низкоуровневые Routing/Matrix/async create/status проверяются через
`python -m connectors.twogis --action ... --request /path/request.json`:
без `--execute` только подсчёт. Асинхронный ответ возвращает ссылку на результат;
автоматического скачивания с произвольного хоста нет.

Официальные справочники:
[Places](https://docs.2gis.com/en/api/search/places/reference/3.0/items),
[Categories](https://docs.2gis.com/en/api/search/categories/overview),
[Routing](https://docs.2gis.com/en/api/navigation/routing/start),
[Public transport](https://docs.2gis.com/en/api/navigation/routing/reference/public_transport),
[Matrix и async](https://docs.2gis.com/en/api/navigation/distance-matrix/start).

### Публикация и чтение

После проверки готовых городов:

```bash
.venv/bin/python -m pipeline.publish_packs \
  --city-dir /tmp/moscow-ready-repeat/moscow \
  --city-dir /tmp/sochi-ready-repeat/sochi --backup /tmp/packs-before-seva
docker compose up --build -d
docker compose run --rm init
```

Публикация проверяет хеши и переключает каталоги Москвы/Сочи с резервной копией.
Шесть автоматических городов не меняются. Резервная копия должна быть новым каталогом
вне репозитория на той же файловой системе. `--built-at` позволяет повторить также
манифест; без него записывается время новой сборки.

Новые API в режиме `db`:

- `GET /api/hotels/<masterId>/geometry` — корпуса, фасады и справочники размещений;
- `GET /api/hotels/<masterId>/nearby-places?category=italian&radius_m=1500` — все места
  с категорией постранично (`limit`, `offset`), без обещания пешей доступности. Пары считает
  запрос PostGIS от точки отеля (`ST_DWithin` + `ST_Distance` по сфероиду WGS84); корпуса
  самого отеля не попадают. Категория — id словаря мест или характеристики каталога (`L01`);
  неизвестная — 422 со списком допустимых;
- `GET /api/hotels/<masterId>/stations` — ближайшие нанесённые станции;
- `GET /api/cities/moscow/transit-times?source_station_id=...&target_station_id=...&departure_at=2026-11-14T02:00:00%2B03:00&profile=metro`
  — датированный ответ или явный `unknown`; неизвестный город — 404.

Эти таблицы и API — вход для агента и поиска. Интеграция новых смыслов запроса в AST
относится к задаче Данила; наличие списка кандидатов не закрывает обязательное условие
«можно пройти пешком». Результаты этапов и измерения — в конце `docs/tasks/seva.md`.

Актуальный полный каталог уже опубликован в штатном `packs/`. Для локальной БД выше

# Интеграционные тесты очищают схему: использовать только отдельную seva_unit_test.

Проверено 358 тестов без пропусков при установленных builder-зависимостях и PostGIS.

Штатный Docker-стек проверен целиком: 8 городов, API и повторный `init` прошли.

### Самостоятельный аудит пакетов и первоисточника

`pipeline.audit_packs` проверяет готовые файлы без БД, сети и API-ключей. Проверка
не меняет входные пакеты. Отчёт и временный индекс должны находиться вне пакетов
и снимка. Для крупных таблиц ключи хранятся в SQLite на диске; индекс удаляется
после прогона. Проверяются также дубликаты между разными файлами одного слоя.

```bash
# Целостность, количество строк, идентификаторы, ссылки, паспорта и покрытие —
# отчёт в репозитории обновляет `make audit`; тест сверяет его с текущими манифестами.
make audit
# Дополнительно сверить весь новый импорт D26 с первоисточником: снимки из релизов данных,
# имя папки снимка = dataset_version в паспортах.
.venv/bin/python -m pipeline.audit_packs \
  --packs packs --snapshot <распакованный снимок>/snapshot_2026-10-24 \
  --snapshot <распакованный снимок>/snapshot_2026-10-27-targeted \
  --work-dir /tmp --report /tmp/seva-pack-audit-with-source.json
# --city moscow --city sochi ограничивает список проверяемых пакетов.
.venv/bin/pytest -q tests/test_pack_audit.py
```

Код возврата: `0` — ошибок нет, `1` — ошибки данных записаны в отчёт, `2` — неверные
аргументы команды. Примеры ошибок ограничены 50 на город, полные количества
сохраняются. Если снимок не указан, первоисточник отмечается `not_checked`.

Аудитор проверяет строки фактов через `Fact`, владельца категории, D26-ограничение
на гарантии, географические координаты, метрики D34, ориентацию фасадов D39,
состояние исходной очереди D33 и покрытие по всему каталогу. Для 2ГИС проверяются
отдельные файлы, даты, `commercial_ok=false` и отсутствие запрещённых полей — и в `source`
строк, и в каждом паспорте списка `sources` фактов. Если в пакете есть корпуса, ссылки на
корпуса и фасады обязаны быть в пакете: `placements.building_id`, фасады окон размещений,
субъекты фактов уровней building / facade / facade_physical_floor. Субъекты файла-слоя
(`"layer": true` в манифесте) пока могут быть в другой схеме id фасадов — это предупреждение
`layer_geometry_subject_not_in_pack`. Место без категории — ошибка. Эти проверки офлайн.

С `--snapshot` задания группируются по исходному файлу: JSON читается один раз.
Сверяются SHA-256 **несжатого JSON**, JSON pointers, `masterId`, поля отеля,
категории, значения/статусы/даты фактов и полнота нового импорта по исходной странице.
HTML-хеш сравнивается с журналом сборщика; сам HTML не проверяется. Непринятые
страницы снимка и геометрия субъектов v9 в пакетах без корпусов не входят в эту сверку.
Факт D26 с пустым `sources` даёт ошибку в отчёте, а не трассировку.

Аудит не заменяет разметку физической точности и измерение запуска Docker.
Итоговые количества, хеши входных манифестов и исходников аудитора, время и пик RSS —
`pipeline/reports/seva_pack_quality_audit.json`.

После дополнения категорий `--snapshot` повторяется для каждого `dataset_version`.
Имя каталога снимка соответствует этой версии; хеши журналов записываются отдельно.
При отсутствии нужного снимка проверка завершается ошибкой `snapshot_dataset_not_supplied`.
Источник с `import_scope=room_categories_only` подтверждает полный список категорий
и D26 этого отеля, сохраняя прежний паспорт координат отеля. Это не освобождает
категории/факты от проверки значений, хешей, указателей и полноты по JSON.

### Проверка демо-ключа без массового сбора

```bash
# Без --execute: только план, даже файл ключа не читается.
.venv/bin/python -m pipeline.check_twogis --env-file .env --report /tmp/twogis-plan.json
# Пять небольших проверок: рубрики, три места, пеший маршрут, метро и Matrix 1×1.
.venv/bin/python -m pipeline.check_twogis --execute --env-file .env \
  --report /tmp/twogis-check.json
```

Непустое окружение имеет приоритет над `.env`; пустое `TWOGIS_API_KEY=` файл не
перекрывает. Если заданы оба источника и значения различаются, в stderr пишется, что
взят ключ из окружения (без значений); источник — `key_source` в отчёте. Файл читается
без исполнения shell. Ключ не передаётся аргументом команды и не входит в отчёт.
`.env.example` содержит только пустой шаблон; остальные `.env*` git игнорирует.
Проверка не добавляет данные в `packs/`, не запускает async/подписку.
`--departure-at` задаёт время с часовым поясом; по умолчанию — завтра в 12:00 Москвы.
Тип ключа — `key_tier` (`demo_key`).

Кеш и месячный бюджет — в общем каталоге (`data/twogis_cache/`). Журнал расхода
ведётся по отпечатку ключа, поэтому его нельзя держать в `/tmp`: после перезагрузки
счётчик начнётся с нуля. Прежний журнал из `/tmp/twogis-shared-cache` перенесите:
`mkdir -p data/twogis_cache && cp /tmp/twogis-shared-cache/budget-*.json data/twogis_cache/`.

Повтор успешного запроса проверяет кеш без нового расхода. В записи кеша есть
`account_fingerprint` — усечённый SHA256 ключа, которым получен ответ. Ответ из кеша
подтверждает доступ, только если отпечаток совпадает с текущим ключом. Ответ другого
ключа даёт статус `from_other_key` без запроса и без расхода. Свежие запросы новым
ключом — только явно, с `--recheck-other-key`: каждый тратит единицы нового ключа
и заменяет запись в кеше.

Причина отказа — `error_kind` и текст `error` (без ключа):
- `dns`, `network`, `network_timeout`, `tls`, `tls_timeout` — сбой соединения, в том числе
  обрыв после отправки запроса (разрыв, RST, обрезанное тело); остальные проверки этого
  хоста пропускаются (`skipped`);
- `http` — HTTP-ошибка с кодом, `api_status` — код в `meta.code`, `redirect` — перенаправление
  (ключ дальше не передаётся), `invalid_response` — не JSON;
- `budget` — исчерпан локальный месячный бюджет, `subscription_required` — async без
  подписки, `cache_mismatch` — запись кеша не совпала с запросом;
- `response_validation` — ответ не прошёл проверку схемы и чисел, `unexpected` —
  непредвиденная ошибка; отчёт пишется в любом случае.

Ошибки сохраняют резерв. Код возврата 1 означает неполный/заблокированный прогон,
а не обязательную невалидность ключа.

Результат 27.10 — `pipeline/reports/seva_twogis_live_check.json`: `blocked`, две
попытки соединения, HTTP-ответов 0; остальные три проверки пропущены. Таймауты там
записаны как `network_timeout`: та версия ещё не отличала TLS-таймаут. Вместе
с предварительной попыткой локально зарезервированы Categories 2 и Routing 1.
Это наш консервативный счётчик, фактический баланс провайдера неизвестен. Поле
`mode: demo` в отчёте позже переименовано в `key_tier: demo_key`; остальное, включая
`code_sha256`, — как в прогоне: хеши относятся к версии кода, которая его выполнила.

Параметры проверены по официальным справочникам:
[Categories и ID Москвы](https://docs.2gis.com/en/api/search/categories/examples),
[Routing](https://docs.2gis.com/en/api/navigation/routing/reference/routing),
[Public Transport](https://docs.2gis.com/en/api/navigation/routing/reference/public_transport),
[Matrix](https://docs.2gis.com/en/api/navigation/distance-matrix/reference/get_dist_matrix).
Для Regions API документация отдельно требует доступ/ключ; этим прогоном он не проверяется.

### Дополнение категорий после ревью №26

Для отелей показа штатным сборщиком получен отдельный снимок
`snapshot_2026-10-27-targeted` (шесть страниц; имя набора — это `dataset_version` паспортов
и часть имён файлов пакета). Это новый источник от 27.10,
не восстановленные данные 24.10. Проверен фактический `masterId` каждого JSON. Снимок нужно
выложить в релиз данных рядом с `data-ostrovok-2026-10-24`: без него сверку D26 этих отелей
повторить нельзя.

```bash
.venv/bin/python -m pipeline.supplement_categories --base-packs <пакеты после finalize_packs> \
  --snapshot <распакованный снимок>/snapshot_2026-10-27-targeted \
  --out /tmp/seva-category-supplement-repeat
```

Команда дополняет только отели без категорий, сохраняет координаты и прежние факты,
пересчитывает покрытие, пишет отдельные JSONL и датированный источник в манифест.
Разница координат больше 50 м требует проверки; пустой `roomGroups` остаётся пустым.
Существующие категории не заменяются. Результат публикуется штатным `publish_packs`.

В геометрическом API добавлен `placement_building_choices`: стабильный ID корпуса,
`mapped_address`, `mapped_name`, `mapped_levels`, подтверждённые `hotel_aliases`,
однозначные фасады и все ID неоднозначной стороны. Это данные для уточняющего вопроса;
этажность OSM не доказывает этажи категории, OSM-имя не становится названием от отеля.
Индекс миграции `0005` ускоряет проверку FK при удалении старых станций; миграция `0006`
добавляет точку места `place.geog` с индексом GiST и `hotel.subzone_id`, удаляет `hotel_place`.
Итог ревью и ограничения — `pipeline/reports/seva_pr26_review.json` и конец задания Севы.
