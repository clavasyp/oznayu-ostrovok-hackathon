# Разбор отчёта ChatGPT v2 «Многогородская система поиска отелей»

- **Отчёт:** `reports/Многогородская система поиска отелей.md`, 609 строк.
- **Рабочие заметки:** `research_notes/Многогородская система поиска отелей/`.
- **Прочитан целиком и сверен Claude 23.10.2026.**

## Главные выводы отчёта

1. **Восемь стартовых городов:** Москва, Петербург, Большой Сочи (центр, Адлер и Сириус отдельно), Казань, Калининград, Минск, Стамбул, Дубай.
   - Батуми — замена Дубаю, если там не пройдёт проверка данных.
   - Следующая волна: Нижний Новгород, Краснодар, Анталья, Тбилиси, Пхукет, Ереван, Алматы.
   - Барселона — только эталон для сравнения.
2. **Уровень A/B/C задаётся по каждому слою отдельно:** `tier_buildings`, `tier_terrain`, `tier_poi`, `tier_transit`, `tier_room_mapping`. Общий бейдж города — только сводка.
   - Ни одному российскому городу не присвоен уровень A.
   - Москва, Петербург и Сочи — B; остальные — C, пока нет проверки.
3. **Пакет города + дельты + отельеры** — лучший вариант по всем критериям (сравнительная матрица 4×10).
   - **Каноничный формат пакета:** `manifest.json`, лицензии, GeoParquet, COG, вычисленные признаки, доказательства, отчёт покрытия.
   - **Дамп PostGIS** — только для быстрого восстановления.
   - **Закрытые данные** (партнёрский каталог, категории отельеров) — отдельный закрытый слой.
4. **Покрытие в админке — четыре слоя:**
   - `raw_presence` — данные есть;
   - `license_admissible` — данные разрешены лицензией;
   - `computable` — признак можно посчитать;
   - `publishable` — значение прошло проверку и публикуется.
   
   Знаменатель — весь каталог отелей города, включая не привязанные к зданиям.
5. **Разные «тишины» — разные признаки:**
   - `outdoor_ln_db` — дБ только из принятой карты;
   - `road_exposure` — факторы окружения;
   - `indoor_quiet` — замер или ответ отельера.
   
   Запасной рецепт допустим только **того же смысла**. Иначе — `unknown` плюс предложение соседнего признака.
6. **Производственный стек:**
   - FastAPI, PostgreSQL/PostGIS/pgvector;
   - S3 (GeoParquet/COG), Dagster;
   - CPU-воркеры DuckDB/GDAL;
   - MapLibre + PMTiles;
   - OpenAI-совместимый LLM-шлюз;
   - Compose локально, Kubernetes в продакшене из тех же образов.
   
   Temporal, Spark/Sedona, Ray/GPU и отдельный поисковый индекс — только по измеренному триггеру.
7. **Смета расчёта горизонтов** (вид и солнце) при 60 точках фасада и 720 азимутах:
   - 1 тыс. отелей ≈ 17 CPU·ч;
   - 10 тыс. ≈ 173 CPU·ч;
   - 100 тыс. ≈ 1728 CPU·ч.
   
   Скорость ядра не измерена, диапазон ×10 в обе стороны.
8. **Цели поиска:** на 100 тыс. отелей при 20 параллельных запросах выборка p95 ≤ 0,5 с, полный ответ p95 ≤ 5 с.
9. **`/health`:**
   - до готовности (миграции, пакеты, контрольный запрос) отвечает 503 с фазой;
   - после готовности — `{"status":"ok"}`;
   - отдельно `/live` и `/ready`.
10. **Российский контур:**
    - по умолчанию Yandex Cloud + YandexGPT (AI Studio, OpenAI-совместимый API);
    - запасной — GigaChat (совместимость частичная, токен на 30 минут);
    - self-host Qwen3-8B (Apache-2.0).
    
    Персональные данные отельеров и запросов — только в российском контуре.
11. **ODbL:** нужна раскрываемая «OSM-ветка» производных данных. Закрытые поля отельеров держать независимо, классификацию утверждает юрист.
12. **План:**
    - **6 ролей:** Data/GIS, backend lead, Agent/NLP/search, frontend, QA/аналитик, DevOps/security.
    - **Две недели:** D1 контракты → D3 первая сборка всех 8 городов → D5 проверка → D7 публикация пакетов → D8 откат → D9–D10 релиз.
    - **Эталон:** 20 отелей × 8 городов ≈ 104–112 человеко-часов.
    - **4–6 недель:** продакшен-профиль, масштаб, отказоустойчивость.
13. **Индустрия** подтверждает разделение: свойства объектов считаются заранее, запрос разбирается онлайн. Google Hotels разделяет физическую комнату, тариф и предложение и поддерживает «все / часть / исключения».

## Что берём

- Восемь стартовых городов → предложено в `decisions.md` (D13), ждёт подтверждения.
- **Пакет города: GeoParquet/COG + манифест как канон, дамп PostGIS — как быстрый путь загрузки** → `design/core.md` §9.
- **Уровни по слоям, а не один на город.** Покрытие в четырёх слоях с полным знаменателем.
- **Семантика рецептов:** запасной рецепт только того же смысла. Разные «тишины» — разные признаки (D15).
- **Лицензионный фильтр** (D14):
  - некоммерческие источники (GBA heights, FABDEM, Ookla Open Data, бесплатный Open-Meteo) не идут в коммерческий контур;
  - для климата в продакшене — ERA5 (CC BY 4.0), платный Open-Meteo или собственный Open-Meteo;
  - для высот в городах уровня C — 3D-GloBFP v2 (CC BY 4.0) после проверки тайлов.
- **`/health` 503 до готовности**, плюс `/live` и `/ready`.
- **Шум вне ЕС:** NoiseCapture (ODbL) как локальные замеры для калибровки модели факторов. Без калибровки публикуем факторы, а не дБ.
- **Разделение «категория / тариф / предложение»** и «все / часть / исключения» для фактов уровня номера.

## Где не согласны или упрощаем

- **Объём набора отелей для запуска.** Отчёт предлагает компактную локальную поставку на 50 отелей на город (255–360 МБ). Мы держим в репозитории **рабочий пакет на полный каталог отелей**, но без тяжёлых слоёв: только отели, их здания, факты с доказательствами и минимальная геометрия для карты. Горизонты, граф, рельеф и полные выгрузки остаются в «сборочном» пакете вне репозитория. Размер замерим на Сочи.
- **Тяжесть стека для хакатона.** Dagster, S3, OpenLineage, OTel, Great Expectations, OIDC, RLS — это целевая продакшен-архитектура. Для сдачи берём то же ядро и те же контракты, но минимум сервисов: Postgres-очередь вместо Dagster на старте, MinIO или локальные файлы вместо S3. Остальное — в профилях compose. Обсуждаем с командой (D16).
- **Строгость формулировок.** Отчёт местами перегружен оговорками. Берём решения и контракты, а не формулировки.
