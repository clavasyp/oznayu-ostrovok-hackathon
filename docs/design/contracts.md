## 1. Факт

- **Поля — как в фактах v9** (`research_notes/Расчёт характеристик/integrated/*_facts.jsonl`): `fact_id`, `hotel_id`, `city_id`, `subject_level`, `subject_id`, `feature_id`, `params`, `value`, `unit`, `status`, `unknown_reason`, `sources`, `recipe_id`, `algorithm_version`, `confidence {level, reason}`, `observed_at`, `calculated_at`, `valid_to`, `scope_note`, `recipe_attempts`, `depends_on`. Лишние поля v9 сохраняются: в базе — в колонке `extra`.
- **ID — текстовые:** `masterId` Островка для отелей, `way/…` для корпусов OSM, 24 hex для фактов (`make_fact_id` — детерминированный).
- **Пути к файлам расчёта — не в `params`**, а в поле факта `evidence_files` (`fan_file`, `target_source_path`, `quality_exclusion_evidence`). Пути — в материалах расчётов от папки проекта (`research_notes/…`); не все эти файлы скопированы в репозиторий. Путей с машины разработчика (`/Users/…` и т. п.) в фактах нет — сборщик пакетов падает, если встретит. Прочие служебные поля в `params` (у B02 — координаты API, хеши) пока остаются — отдельная задача.
- **Статусы:** `observed | computed | estimate | ostrovok_content | curated | hotelier | simulated_hotelier | unknown | not_applicable`.
- **Правила, которые проверяет модель:**
  - у `unknown` обязательна `unknown_reason`;
  - у статуса со значением обязательно `value`.
- **Вид и солнце из окна** (V01, V05; `calculators/view_sun.py`, D40): `value = {"visible": bool, "why": …, "blocker": …}`; `why` — `clear`, `sun_behind_facade`, `sun_behind_facade_all_year`, `blocked`, `no_sea`; `blocker` — здание или источник, который закрывает. Поле по умолчанию у V01–V05 в каталоге — `visible`. Уровень — `facade_physical_floor` («здание:фасад:floorN»; этажи 1…N по OSM) или `facade` («здание:фасад») — только если ответ не зависит от этажа (Солнце за стеной, моря в секторе нет) или этажность неизвестна. У «неизвестно» в `depends_on[0]` — `decided_by` (здание, от высоты которого зависит ответ) и `decided_by_kind`. Рядом с «неизвестно» может лежать факт `estimate` того же места — оценка по центральным значениям (D18). Параметры V05: `date`, `last_minutes = 30`; факт без `date` — «в любую дату» (закат за стеной круглый год).
- **Обязательное условие** закрывают только `observed`, `computed`, `ostrovok_content`, `curated`, `hotelier`, `simulated_hotelier` — и только если `hard_condition_eligible` не `false`. Оценки — нет (D18). См. `Fact.usable_in_hard`.

## 2. Плагин

Калькулятор: `id`, `version` (→ `algorithm_version`), `feature_ids`, `run(subjects, ctx) -> list[Fact]`. Регистрация — декоратор `@register_calculator`. Неудача рецепта — факт `unknown` с причиной и `recipe_attempts`, а не исключение. Коннектор: `available(ctx)`, `fetch(ctx, workdir) -> list[DatasetRef]`.

## 3. AST

`hard` / `soft` (с `weight`) / `clarify` / **`out_of_catalog`** (D34: части запроса без характеристики не теряются). Условие: `feature_id` (ID каталога), `op`, `value`, `field` (какое поле значения сравнивать: `distance_m`, `count`, `mean`…), `params` (месяц, цель маршрута, время), `binding` (`same_placement` для уровня номера, D17). Компактную схему для модели (ограничения Claude на схемы) делает Данил.

**Без потерь (по черновику v11):**
- у условия и у части вне каталога есть `atom_id`;
- `span` — позиции в Unicode code points, полуинтервал `[start, end)`;
- `provenance` (явно / выведено) и `mapping` (точно / частично / другой смысл).

**Вне каталога:** у части запроса есть `requiredness`. Обязательная часть вне каталога даёт «Нужно уточнить», а не «Подходит».

**Место рядом** («рядом итальянский ресторан», «музей в 10 минутах»): часть вне каталога с `nearest_contracts: ["nearby_place"]`, `normalized = "nearby_place:<категория>"` и полем `place`:
- `category`, `label` — из словаря мест `agents/catalog/places.json` (слова гостя → метки OSM, рубрики 2ГИС);
- `radius_m` пешком: расстояние гостя (`radius_source = guest`) или «рядом» = 800 м (`policy`);
- `on_site = true` — место в самом отеле («отель с бассейном», «ресторан в отеле»), радиуса нет;
- `quality` — слова гостя о качестве («хорошие», «вкусные»): проверить нечем, рейтингов нет.

**Поиск считает место на запросе** (`core/search.py` `place_item`, `Store.nearest_places` — PostGIS по местам пакета, свои корпуса не в счёт). Пункт выдачи: `label`, `nearby {category, radius_m}`, `place {place_id, name, distance_m, source}`; обязательное — в `hard`, иначе в `soft` с весом 0,5.
- «да» — место категории в радиусе с запасом на обход (расстояние по прямой × 1,3 ≤ радиус);
- «нет» не бывает: места карт — не перепись. `place_not_found` (склоняется к «нет»), `place_far_on_foot` (к «да»), `place_quality_unknown`, `place_no_data` (о таких местах в городе данных нет), `place_on_site` (спросим отель) — «неизвестно».

**Логика:** необязательный граф `logic` (`ATOM` / `AND` / `OR` / `NOT`) + `hard_root`; пусто — все `hard` через AND. Трёхзначная логика — `core/verdict.py`: `not3`, `and3`, `or3`; пустое OR = неизвестно. `unparsed_spans` — неразобранные фрагменты.
- Движок считает граф любой вложенности (`core/search.py`, класс `Logic`). `ATOM` ссылается на `atom_id` условия из `hard` или части вне каталога; часть вне каталога в графе — «неизвестно» на своём месте: «A ИЛИ (вне каталога)» при A = «да» — «да».
- Условия вне графа и обязательные части вне каталога соединяются с графом через AND.
- Битый граф — нет корня, цикл, `NOT` не с одним ребёнком, атом без условия — даёт «неизвестно», а не «да».
- **Непонятое рядом с «обязательно»** (D38): разбор кладёт его в `out_of_catalog` с `requiredness: required` — отель не выше «Нужно уточнить».

**Источник** — интерфейс `core.store.Store`: база (`core/store_db.py`, `DATA_MODE=db`, так у жюри) или заглушки из фактов v9 (`app/stub_store.py`, `DATA_MODE=fixtures`). Формы ответов одинаковые; флаг `"stub"` говорит, откуда данные.

**Поиск** — `core/search.py`. Уровень условия определяется по фактам характеристики у отеля.

- **Отель, корпус, маршрут.** Факты группируются по месту: субъект плюс параметры.
  - «Да» — только если «да» на каждом месте; «нет» — если «нет» везде; при `quantifier: any` хватает одного «да».
  - Корпуса расходятся — `depends_on_building`. Источники расходятся на одном месте — `conflict` и `conflict_fact_ids`.
- **Категория номера** (`subject_level = room_type`) — по каждой категории.
- **Окно** (`facade_physical_floor`, «здание:фасад:floorN») — по размещениям категории (D17).
  - Все такие условия проверяются **вместе на одном размещении**: «закат на 5-м, тишина на 2-м» — это «не подходит» (`no_single_placement`).
  - Категория подходит, только если список размещений полный (`complete`) и на каждом размещении все условия «да».
  - Часть размещений «да» — `depends_on_room` или `not_guaranteed`. Нет размещений — `no_placements`.
  - Виду и солнцу хватает одного окна углового номера, остальному нужны все окна.
- **Этаж** (`floor`, D39) — не факт, а поле размещения из ответа отеля (номер этажа, как его называет отель). Проверяется на каждом размещении вместе с условиями окна. Нет размещений — `no_placements`.
- **Факт фасада** (`subject_level = facade`, «здание:фасад») — про все окна этого фасада на любом этаже, например «окна во двор».
- **Окна отеля без категорий** (`hotel_windows`, D40): у отеля нет категорий с размещениями, а факты окон есть — условие окна проверяется по всем окнам корпусов отеля. Итог — всегда «неизвестно»: корпуса отеля мы знаем не все, а где будет номер, скажет отель.
  - коды: `window_some` / `window_all` — по расчёту «да» в части / во всех окнах; `no_window_known` — по расчёту «нет» во всех окнах известных корпусов; `estimate_only` — «да» только по оценке; `no_fact_params` — факты окон есть, но не на эти даты; иначе — частая причина окон;
  - в пункте — `windows`: `yes`, `no`, `estimate` — `{сторона из 8: [этажи]}` (этаж `0` — весь фасад); `count` — сколько окон; `want` — значение условия (у «без вида» — `false`); `estimate_none: true` — по оценке ни из одного окна. «Да» и «нет» — только по расчёту, оценка — отдельно, и для желательных условий тоже;
  - `fact_ids` — факты окон, на которых держится сказанное: «да» по расчёту, иначе «нет» по расчёту, иначе оценки; не больше 2 на окно и 60 всего;
  - объяснение говорит в полярности гостя: у «без вида на закат» (НЕ или `visible = false`) подходят окна без заката.
- **Параметры-ключи** (D15): факт V05 на дату отвечает только на запрос с той же датой; запрос без даты видит только факты без даты.
- **С графом `logic`** весь запрос считается на каждом размещении: условия отеля, категории и окна вместе. «Закат ИЛИ тишина»: у одного номера закат, у другого тишина — подходят оба. `verdict` размещения в `placements` — по всему запросу.
- **Пункты `hard` по графу:**
  - верхнее «И» раскрыто;
  - «ИЛИ» и вложенные группы — один пункт `{op, verdict, items, text_span}`, где `items` — варианты;
  - «НЕ» — то же условие с `negated: true` и уже перевёрнутым `verdict`;
  - у пункта условия есть `atom_id`.
- **Подписи для экрана** (у пунктов `hard`, `soft` и условий категорий, в группах — тоже):
  - `label` — словами гостя (`text_span`): «без собак», «заселиться ночью»; у `negated` без слова отрицания — «не …». Рядом с вердиктом показывать его: правила переворачивают «без собак» в «можно только с кошкой или без животных», и «можно с животным: нет» читалось бы наоборот;
  - `feature_name` — название характеристики, у поля не по умолчанию — с уточнением: «можно с животным (максимальная масса животного)»; у группы — `null`.
- **Наличие без поля да / нет** (D39): «нет» — `none`, «есть, тип не назван» — `present`.
  - `present` против конкретного типа (`eq "split"`, `in [...]`) — «неизвестно», код `value_unspecified`;
  - `ne "none"` и `exists` при `present` — «да»; при `none` — «нет».
- **Отель подходит, если подходит хотя бы одна категория.** В ответе: `categories` (вердикт, статус, размещения) и `best_category`.
- **Оценки** в обязательных условиях не участвуют (D18).
- **Причины:** код `reason_code` и текст для экрана `reason` (`core/reasons.py`). У фактов в API — `unknown_reason_text`.

## Ответ отельера → факт → пересчёт (`core/hotelier.py`)

**Тело `POST /api/hotelier/{id}/answers`:**
- `question_id` или `feature_id`;
- `fields` — поля ровно с именами из вопроса (`parsed_fields`); лишнее — 422, а не догадка;
- `params` — к каким параметрам характеристики относится ответ (D15);
- `dont_know`, `answer_text`;
- `room_type_id` — ответ про категорию;
- `placements` — этажи и стороны номеров категории: `completeness`, `guarantee`, `items` = явные пары `building_id × floor × windows` (D17). Пункты одного здания и этажа — один номер, их окна сливаются (угловой); `room_variant` разводит разные номера на этаже: «окна на юг» — номер на одной из южных стен, на каждую стену свой вариант (D41-3). Ответ имитатора не заменяет набор настоящего отеля или команды (D41-8);
- `is_simulated`;
- `ast` — показать статус до и после.

**Правила:**
- **Статус факта:** `hotelier`; у имитатора — `simulated_hotelier` с пометкой (D31). Значение — поля ответа, в паспорте — цитата, вопрос, время.
- **Замена:** новое заявление отеля заменяет его прежние заявления о том же месте — данные Островка (D26), прошлые ответы. У старых фактов `is_current = false` и `superseded_by`. Имитатор настоящий ответ не заменяет.
- **Наш расчёт** (`computed`, `observed`, `curated`) ответ не заменяет. При расхождении — запись в `conflict`, а поиск показывает «нужно уточнить» (`conflict_fact_ids`).
- **«Не знаю»** — факт `unknown` (`hotelier_does_not_know`), известное не отменяет.
- **Текст без полей** — `answered_unparsed`: ждёт агента-отельера, факта нет.
- **Пересчёт:** поиск читает только действующие факты, поэтому новая выдача видна сразу. Производные расчёты (вид по новым этажам) пересчитают калькуляторы.

## Кандидаты и непокрытые части запроса (D33, D34, черновик v11)

- **`curation_item`** — кандидат от ИИ или Codex.
- **`curation_claim`** — его дочерние утверждения (кухня, часы, часы кухни, координаты, рейтинг) со своими доказательствами. Человек принимает поля по одному. Факт `curated` создаётся только из принятого поля.
- **`unmatched_atom`** — по событию на каждую непокрытую часть запроса: запрос, атом, фрагмент, страта (`live` / `review` / `synthetic`), обязательность, ближайшие контракты, статус работы. Частота — число разных запросов в окне.

## 5. Пакет города

См. `packs/FORMAT.md`. `init`:
1. миграции;
2. проверка sha256 каждого файла по `manifest.json`;
3. загрузка в базу;
4. запись в `pack_load`.

Повторный запуск с тем же манифестом ничего не делает.

**Новая версия пакета заменяет данные города целиком.**
- Факты из пакета помечены версией в `extra.pack`. Факты, созданные в работе (ответ отельера, проверка командой), остаются.
- Вопросы отельеру из пакета пересоздаются: в dev-базе ответы на них при смене пакета сбрасываются.

**Корпуса и фасады** (D39, черновик — договариваемся с Севой). По ним агент-отельер переводит ответ «корпус 2, этажи 3–5, окна на запад» в размещения, а поиск проверяет «окна во двор»:
- корпус — `building_id` (OSM `way/…`), `hotel_id`, названия, как его зовёт отель («корпус 2», «главный»);
- фасад — `facade_id`, `building_id`, азимут, сторона из 8 (`N` … `NW`), `is_courtyard`;
- категории — `room_types` из `roomGroups` Островка.

**Слои калькуляторов** — файлы пакета, которые собирает не сборка v9, а отдельный калькулятор (сейчас — вид и солнце Сочи, `python -m pipeline.build_view_sun`, нужна группа `builder` и материалы расчётов вне репозитория):
- `core.packs.add_layer` добавляет файл в `manifest.json`, его источники помечает полем `layer` (путь файла), к `pack_version` добавляет хеш слоёв: `<версия сборки>+<хеш слоёв>` (`v9-…+xxxxxxxx`, `category-supplement.2-…+xxxxxxxx`), покрытие (`coverage`) пересчитывает по всем фактам вместе со слоем (`refresh_coverage`);
- пересборка слои сохраняет (`keep_layers`; публикация `publish_packs` — тоже, с пересчётом покрытия), а в общий `facts` их не вливает (`pack_parts`).

**Этажность, проверенная командой** (D33) — `data/curated/<город>_building_heights.csv`: `building_id`, `levels` или `height_m`, `source`, `source_url`, `checked_by`, `checked_at`, `note`. Строка без этажности — очередь «проверить по картам», её пишет сборка слоя (колонки `now_known`, `cells`, `hotels` и ссылки на OSM, Яндекс, 2ГИС). Заполненная строка без проверяющего, даты или ссылки — ошибка сборки.

**Что лежит в `packs/` сейчас** — 8 городов из расчётов v9 (`python -m pipeline.build_v9_packs`): отели когорты, факты, вопросы с предзаполнением, покрытие (`coverage`), сверка с Островком (`ota_comparisons`). Сборка детерминированная. Каталог Островка и данные карт добавляются в тот же пакет города своими файлами.

## Что решить на ревью

1. **Имена полей как в v9** — уже так (рекомендация).
2. **Текстовые ID** вместо bigint. v11 советует для продакшена bigint и таблицу алиасов; для хакатона текст проще.
3. **Формат пакета — JSONL.gz,** а не GeoParquet: v9 пишет JSONL, а образу `api` не нужен pyarrow. Быстрый путь `pg_dump` можно добавить позже.
4. **Первая миграция строит схему из моделей** (`create_all`); дальше — обычные ревизии `alembic revision --autogenerate`.
