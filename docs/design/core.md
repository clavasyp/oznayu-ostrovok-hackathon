## 1. Компоненты

| Сервис (compose) | Что делает | Технология |
|---|---|---|
| `db` | Факты, геометрия, спецификации, вопросы, очереди задач на старте | PostgreSQL 16 + PostGIS 3.4 (версии зафиксированы) |
| `app` | API, раздача фронтенда, `/health`, миграции и загрузка пакетов городов при старте | Python 3.12, FastAPI, SQLAlchemy / psycopg, Alembic |
| `worker` | Коннекторы, калькуляторы, планировщик актуализации, агент-отельер в фоне | Тот же образ, другая команда. В compose под профилем `full`, для запуска жюри не обязателен |
| LLM | Разбор запроса, разбор ответов отельера, текст в спецификацию, объяснения | Шлюз с двумя адаптерами (D21): Anthropic SDK (Claude Opus 5.5, основной) и OpenAI-совместимый (YandexGPT / GigaChat, запасные). Выбор через `LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` |

**Состав запуска по D16:**
- `db`;
- `app` (API + UI);
- Dagster (webserver, daemon, code location);
- S3-совместимое хранилище **SeaweedFS** (D16; MinIO заменён, т.к. архивирован);
- одноразовый `init` для миграций и загрузки пакетов.

Тяжёлые расчёты уже лежат в пакетах городов. Укладывается ли запуск в 10 минут — проверяем замером.

**Образы — targets одного Dockerfile (отчёт v4a):**
- **`api`** — FastAPI, psycopg, Alembic, opening-hours-py; без GDAL и JDK;
- **`builder`** — Dagster с геостеком: shapely, geopandas, pyosmium, osmnx, rasterio, pvlib, duckdb…;
- **тяжёлые профили** — GRASS, Valhalla, OTP / r5py.

Подробно: `docs/research/review_gpt_v4a.md`.

## 2. Модель данных

### 2.1 Объекты

Обновлено по отчёту v3 (D17).

```
city ─┬─ hotel ─┬─ source_alias           (id отеля во внешних источниках, с версиями)
      │         ├─ classification         (звёзды: схема, орган, сырое значение, срок)
      │         ├─ hotel_building ── building ── building_part ─┬─ facade
      │         │                                                └─ physical_floor
      │         └─ room_type ─┬─ bed_configuration, occupancy_policy
      │                       └─ placement_set ── placement (часть здания + физ. этаж) ── placement_window (фасад)
      ├─ dataset_version                   (снимок слоя: OSM, рельеф, GTFS… с датой и лицензией)
      └─ layer tables (osm_paths, poi, beach, transit_stop…) — сырые слои по городу
```

| Таблица | Ключевые поля |
|---|---|
| `city` | `id`, `name`, `boundary geom`, `timezone`, `pack_version`, `tier_buildings` / `tier_terrain` / `tier_poi` / `tier_transit` / `tier_room_mapping` |
| `source` | `id`, `name`, `url`, `license`, `license_commercial_ok` (bool), `notes` |
| `dataset_version` | `id`, `city_id`, `source_id`, `layer`, `release`, `observed_from/to`, `published_at`, `fetched_at`, `content_hash`, `row_count` |
| `hotel` | `id` (свой UUID), `city_id`, `name`, `lodging_kind`, `address`, `geom point`, `status` (сырой статус из источника; при недоступности — `stale`, а не «закрыт») |
| `source_alias` | `hotel_id`, `namespace` (ostrovok — основное, ID `mid`; osm, overture, fsa_registry…), `external_id`, `source_version`, `first_seen`, `last_seen`, `match_score` (порядковый, не вероятность) |
| `merge_log` | Слияния и разделения отелей с причиной и возможностью отката |
| `classification` | `hotel_id`, `scheme`, `authority`, `class_raw`, `parsed_class`, `certificate`, `valid_to`. Звёзды разных систем не усредняются |
| `building` | `id`, `city_id`, `geom polygon`, `levels`, `height_min_m`, `height_max_m`, `height_source`, `year_built`, `ground_elev_m` |
| `building_part` | `id`, `building_id`, `geom`, `levels` (крыло или часть с другой этажностью) |
| `physical_floor` | `id`, `building_part_id`, `ordinal`, `display_label` («PB», «мансарда», «5»), `level_kind`, `z_view_min_m` / `z_view_max_m`. Правила «этаж = 3 м» как измерения нет; источник высоты в паспорте |
| `hotel_building` | `hotel_id`, `building_id`, `role` (main/annex), `match_method`, `confidence` |
| `facade` | `id`, `building_part_id`, `geom linestring`, `azimuth_deg` (наружная нормаль), `length_m`, `is_courtyard` |
| `room_type` | `id`, `hotel_id`, `name`, `source`. Это физическая категория; тарифы и предложения в ядро не входят |
| `room_type_alias` | Связь с категориями поставщиков: `exact` / `narrower` / `broader` / `overlap` / `rejected` (многие ко многим, неточные — на ревью) |
| `bed_configuration`, `occupancy_policy` | Варианты кроватей (не суммируются) и правила размещения |
| `placement_set` | `room_type_id`, `completeness` (complete / partial / unknown), `guarantee` (all_guaranteed / some_possible / on_request / exact_room), `version`, `fact_id` |
| `placement` | `placement_set_id`, `building_part_id`, `physical_floor_id` |
| `placement_window` | `placement_id`, `facade_id` (у углового номера — несколько окон) |

**Почему не массивы фасадов и этажей.** Из «восток 1–3, запад 4–5» в виде двух массивов получаются ложные варианты «восток-5» и «запад-1». Поэтому размещение — это список конкретных пар «этаж × окна».

### 2.2 Ядро: факты и всё вокруг них

```sql
CREATE TABLE feature (            -- загруженная спецификация характеристики
  id text, version int, spec jsonb, family text, subject_level text,
  status text,                    -- active | draft | retired
  PRIMARY KEY (id, version)
);

CREATE TABLE fact (
  id bigserial PRIMARY KEY,
  city_id int, subject_level text, subject_id bigint,   -- hotel | building | building_part | facade | physical_floor | room_type | route
  feature_id text, feature_version int,
  params jsonb,                   -- параметры параметрических признаков: цель маршрута, дата/время, интервал часов…
  value jsonb,                    -- число, интервал, enum, bool или значения по этажам
  quantifier text,                -- для уровня категории: all | some | none
  status text,                    -- observed | computed | estimate | ostrovok_content | curated | hotelier | simulated_hotelier | unknown | not_applicable
  unknown_reason text,            -- no_data | no_coverage | stale | license | scope_conflict | no_floor_mapping | compute_failed
  confidence text,                -- high | medium | low
  confidence_reason text,
  recipe_id text, algo_version text,
  sources jsonb,                  -- [{source_id, dataset_version_id, url, license}]
  observed_from timestamptz, observed_to timestamptz,
  published_at timestamptz, fetched_at timestamptz,
  valid_from timestamptz, valid_to timestamptz,         -- прогнозы, события, котировки
  computed_at timestamptz, expires_at timestamptz,
  scope_note text,                -- «только западный фасад, этажи 5+»
  is_current bool, superseded_by bigint
);

CREATE TABLE fact_dependency (fact_id bigint, depends_on_dataset bigint, depends_on_fact bigint);

CREATE TABLE conflict (
  id bigserial, feature_id text, subject_level text, subject_id bigint,
  fact_a bigint, fact_b bigint, state text,  -- detected | awaiting_evidence | resolved | reopened
  resolution_rule text, resolved_fact bigint, question_id bigint, updated_at timestamptz
);

CREATE TABLE question (            -- вопрос отельеру
  id bigserial, hotel_id bigint, feature_id text, subject_level text, subject_id bigint,
  text text, priority real, reason text,        -- unknown | conflict | low_confidence | expired
  state text, asked_at timestamptz, answer_text text, answered_at timestamptz,
  parsed jsonb, is_simulated bool
);

CREATE TABLE curation_item (       -- D33: кандидат ручной обработки командой с ИИ; ещё не факт
  id bigserial, city_id int,
  kind text,                       -- match_hotel_building | beach_entrance | view_check | text_extract | event | category_facade …
  subject_level text, subject_id bigint, feature_id text,
  proposal jsonb,                  -- предложенное значение или связь
  proposed_by text,                -- 'llm:<model>' | 'script:<name>' | 'codex'
  evidence jsonb,                  -- [{url|file, sha256, quote|bbox, license}]
  state text,                      -- proposed | accepted | corrected | rejected | unsure
  reviewer text, reviewed_at timestamptz, review_minutes real, note text,
  fact_id bigint                   -- факт `curated` после accepted / corrected
);

CREATE TABLE audit_log (id bigserial, actor text, action text, entity text, entity_id bigint, diff jsonb, at timestamptz);
```

**Значения по этажам.** У фасадных характеристик значение хранится по физическим этажам (`physical_floor.ordinal`):

```json
{"by_floor": {"1": false, "2": false, "3": "unknown", "4": true, "5": true}}
```

Так один факт отвечает и на «с какого этажа видно море», и на «этаж ≤ 3».

**Параметрические признаки.** Это «аптека, открытая в момент приезда», «время из аэропорта к 01:30», «солнце 14–18 в июле», «события в даты поездки».
- Вариант с типовыми параметрами (цели маршрутов, месяцы) предрасчитывается: параметры лежат в `params`.
- Конкретная дата и время пользователя считаются в момент запроса из сохранённых входов (часы работы, расписание, профиль горизонта) и не пишутся в `fact`.

**Статусы:**
- `not_applicable` — признак неприменим, например моря нет. Это не «неизвестно».
- `estimate` — оценка ниже порога публикации (D18). В обязательных условиях не участвует.
- `simulated_hotelier` в реальное покрытие не входит, считается отдельно.
- `curated` (D33) — обработано командой с ИИ и **проверено человеком**. Создаётся только из `curation_item` в состоянии `accepted` / `corrected`; проверяющий и доказательства обязательны. В обязательных условиях — только при доказательстве из первоисточника того же смысла. Непроверенный кандидат фактом не является.

### 2.3 Почему классическое хранение, а не RAG (D20, принято)

**Источник правды — реляционная модель в PostgreSQL + PostGIS:** объекты, факты с паспортами, геометрия. Поиск — это SQL с трёхзначными условиями и пространственными предикатами.

RAG и векторный поиск как основа не подходят:
- **Векторный поиск находит «похожее», а не «верное».** Он не гарантирует условие «этаж ≤ 3 И вид на море = да» и не различает «нет» и «неизвестно». У нас обязательное условие проходит только при доказанном «да» (D5).
- **Наши данные структурные:** числа, интервалы, да/нет, геометрия, даты. Их честно хранить типизированными значениями, а не кусками текста.
- **Нужен паспорт у каждого значения:** источник, дата, уверенность, срок годности, зависимости для пересчёта. У фрагмента текста в векторной базе этого нет.
- **Бриф прямо запрещает** путь «спросить LLM по найденным текстам».

**LLM получает данные как JSON фактов с ID**, а не как найденные куски текста. Это тоже «опора на данные» (grounding), но без векторного поиска.

**Где векторы всё-таки полезны** — вторичные задачи, через расширение `pgvector` в той же базе, без отдельной векторной БД:

| Задача | Как | Ограничение |
|---|---|---|
| Сопоставить слова пользователя с характеристиками каталога («чтобы не было солнца» → `direct_sun_hours`) | Эмбеддинги описаний и синонимов спецификаций. Пока характеристик ~80, хватит каталога в промпте LLM; векторы нужны при сотнях | Только выбор ID характеристики, не значения |
| Извлечение фактов из неструктурированных текстов при сборке: сайты отелей, свободные ответы отельеров, разрешённые отзывы | Найти нужный фрагмент → LLM извлекает поле → сохраняется как **факт с доказательством** (ссылка на фрагмент) | Это этап сборки. В момент поиска тексты не участвуют |
| Мягкие запросы вне каталога («уютный бутик-отель», «атмосферно») | Сходство с описанием отеля как слабый мягкий сигнал с пометкой «по описанию» | Никогда не жёсткое условие |
| Поиск дублей по названиям | Эмбеддинги имён как один из признаков пары | Решают правила и ревью (D17) |

**Как хранятся факты и как устроен поиск:**
- **`fact`** — неизменяемая история с паспортами. Новые характеристики добавляются без миграций схемы.
- **`current_features`** — материализованная проекция текущих значений для поиска. Индексы по `(city_id, feature_id)` и по значениям, GIN по `jsonb`. Часто используемые признаки при необходимости выносятся в отдельные колонки.
- **Объём:** 100 тыс. отелей × ~100 признаков ≈ 10 млн строк. Это обычный объём для PostgreSQL. Отдельный поисковый движок вводим только при измеренном провале цели p95 (см. отчёт v2).
- **Пакеты городов** переносятся в GeoParquet (§9) и загружаются в эти же таблицы.

## 3. Спецификация характеристики

Одна характеристика — один YAML-файл в `specs/`. Добавить характеристику значит добавить файл: руками или из текста через LLM (раздел 7.4).

```yaml
id: walk_to_beach
version: 1
title: Пешком до пляжа
family: walkability
subject_level: hotel
value:                       # что утверждаем
  distance_m:    {type: number,   unit: m}
  time_min:      {type: interval, unit: min}
  ascent_m:      {type: interval, unit: m}
  stairs:        {type: integer}         # участков-лестниц по пути
  busy_crossings: {type: integer}        # переходов через оживлённые дороги
search:                      # как можно спрашивать
  default_field: time_min
  operators: [lte]
  synonyms: ["до моря", "до пляжа пешком", "близко к морю"]
recipes:                     # от лучшего к худшему; все дают ТОТ ЖЕ смысл (D15)
  - id: osm_graph_dem
    kind: computed
    calculator: walk_route@1
    targets: beach_access
    requires:                # проверяется ПО ОБЪЕКТУ: есть ли связный граф от входа отеля до входа на пляж
      layers: [osm_paths, beach, dem]
      object_check: route_connected
    confidence: medium
    publish: {ascent_m: estimate_if_dsm}   # подъём по DSM 30 м — только оценка (D18)
  - id: ask_hotelier
    kind: hotelier
    question: >
      Сколько минут идти от входа в отель до ближайшего пляжа?
      Есть ли по пути лестницы или переход через оживлённую дорогу?
    parse_to: [time_min, stairs, busy_crossings]
related:                     # соседние признаки другого смысла — не рецепты
  - beach_straight_distance  # «по прямой» — отдельный признак-подсказка
ttl_days: 90
```

**Правила цепочки рецептов** (отчёт v3):
- рецепт доступен, если **для этого объекта** есть права, поля, покрытие и пройден порог качества;
- уровень города — только подсказка, где искать данные;
- к следующему рецепту переходим **только при `unknown`**: валидное «нет» останавливает цепочку;
- два пригодных рецепта противоречат друг другу → `conflict`, а не «побеждает первый».

Ещё примеры (сокращённо):

| id | Уровень | Рецепты | Значение |
|---|---|---|---|
| `sea_view` | facade | `los_target@1` (здания, рельеф, полигон моря) → вопрос отельеру | `by_floor`: да / нет / неизвестно + видимый сектор |
| `direct_sun_hours` | facade | `sun_on_facade@1` (горизонт, солнце по датам) | `by_floor`: часы по месяцам |
| `outdoor_ln_db` | facade | `official_noise_map` (только где есть принятая карта) → иначе `unknown` | Ln в дБ, интервал, год карты |
| `road_exposure` | facade | `noise_factors@1` (трассы, ж/д, бары, аэропорт из OSM; калибровка по NoiseCapture, где есть замеры) | `low/medium/high` + перечень факторов с расстояниями, без дБ |
| `indoor_quiet` | room_type | вопрос отельеру или замер | да / нет / неизвестно + условия (окно закрыто или открыто) |
| `night_pharmacy` | hotel (параметр: момент) | `poi_open_at@1` (OSM `opening_hours`) | ближайшая открытая в этот момент + путь |
| `pet_policy` | room_type | вопрос отельеру | вид, вес, доплата |
| `sea_temp_by_month` | морская ячейка | Open-Meteo Marine (D22; модельная температура верхнего слоя) | °C по месяцам с пометкой «модель, ячейка» |
| `airport_transfer` | hotel (параметр: дата и время) | `transit_route@1` по действующему GTFS → маршрутизация карт (D35) → иначе **`unknown`**, а не «упрощённо» | время, пересадки, последний рейс |

Полный каталог из 80 характеристик с шаблонами рецептов — `docs/research/review_gpt_v3.md`. Нумерация ID (V01, W01…) берётся оттуда.

## 4. Коннекторы (готовые данные)

```python
class Connector(Protocol):
    id: str                      # "osm_pbf"
    source_id: str               # ссылка на запись в таблице source (лицензия)
    layers: list[str]            # какие слои производит
    def available(self, city: City) -> bool: ...
    def fetch(self, city: City, workdir: Path) -> list[DatasetVersion]: ...   # скачать + нормализовать в PostGIS
```

**Первый набор:**

| Коннектор | Слои |
|---|---|
| `osm_pbf` (выгрузка Geofabrik, обрезка по границе города; чтение через pyosmium — OSMnx не читает PBF) | `building`, `poi`, `osm_paths`, `roads`, `beach`, `transit_routes`, `trees` |
| `copernicus_dem` | `dem` |
| `open_meteo_climate` | климат по месяцам (Historical API: ERA5 + ERA5-Land 11 км + ECMWF IFS 9 км). Единственный источник погоды и климата (D22). **Хакатон: бесплатный API**, разовый сбор при сборке пакетов, лимит 10 тыс. запросов в сутки. **Продакшен: Professional** (нужен для Historical / Climate) **или свой сервер.** Модель задаём явно (`era5_land` / `era5`), норма 1991–2020. Атрибуция CC BY 4.0 |
| `open_meteo_marine` | температура моря, волны (D22) |
| `yandex_maps`, `2gis`, `google_maps` (D35: разрешено организаторами) | `poi`: категории, кухня, часы, рейтинг и число оценок; `routing`: время на общественном транспорте и на машине с пробками в типовые часы; `panorama`: кадры для вида, этажности, фасадов. Источник, ID объекта и дата — в паспорте. Способ доступа (API или страницы) и ключи — по итогам v11 |
| `open_meteo_air` | воздух, пыльца, UV (D22) |
| `ostrovok_site` | **Основной источник каталога (D24):** sitemap → страницы отелей → `__NEXT_DATA__` и JSON-LD. Отели, этажность и год постройки, номер в реестре ФСА, категории номеров (`roomGroups`), удобства, правила, POI с расстояниями. `robots.txt` игнорировать разрешено организаторами, поэтому доступны отзывы и выдача. Сбор вежливый: около 1 запроса в секунду на поток. Факты получают статус `ostrovok_content`. **По v5:** `external_id` = фактический `masterId`; ключ категории = (`masterId`, `rgHash`, версия); после сбора фильтр по координатам (чужие города, США); 307 = устаревший URL; перепись по `facts.kind`; храним сырой gzip + хеш + JSON pointer; нули и UNSPECIFIED = неизвестно. Схема и заполненность — `docs/research/ostrovok_site_probe.md`, `docs/research/review_gpt_v5.md` |
| `fsa_registry` | Россия: номер записи в реестре берём со страниц Островка (`facts.register`, D19); сверка по ссылке на tourism.fsa.gov.ru — выборочно |
| `overture_places` | POI и отели. Релизы живут 60 дней — снимок с хешем обязателен |
| `gtfs` | расписания (где есть фид) |
| `wikidata` | достопримечательности, год постройки |

Позже:
- глобальные высоты зданий ⏳ лицензия;
- адаптеры городских порталов (уровень A).

## 5. Калькуляторы (вычисляемые данные)

```python
class Calculator(Protocol):
    id: str; version: str        # "walk_route", "1"
    inputs: list[str]            # слои и/или характеристики
    subject_level: str
    def compute(self, city: City, subjects: list[int], params: dict) -> list[FactDraft]: ...
```

**Правила:**
- расчёт детерминированный: одинаковые входы дают одинаковый результат;
- у каждого калькулятора есть юнит-тесты на синтетических сценах;
- калькулятор пишет `confidence` с причиной и `depends_on`.

**Первый набор:**

| Калькулятор | Что делает |
|---|---|
| `hotel_building_match` | Отель → здания |
| `facades` | Стороны здания с нормалями |
| `building_height` | Этажность → высота интервалом; тег `height` → точнее |
| `walk_route` | Граф OSM и рельеф: длина, время, подъём, лестницы, переходы |
| `straight_distance` | Расстояние по прямой |
| `poi_open_at` | Разбор `opening_hours` на дату и время |
| `los_target` | Видимость цели с точки фасада по этажам |
| `sun_on_facade` | Часы прямого солнца по месяцам |
| `noise_proxy` | Шум по факторам окружения |
| `airport_transfer` | Маршрут по GTFS |
| `green_share` | Доля зелени вокруг |
| `climate_profile` | Климат по месяцам |

## 6. Выбор рецепта и покрытие

Для каждой характеристики в городе:

```
для каждого объекта:
    для каждого рецепта по порядку:
        если рецепт недоступен для ЭТОГО объекта (права / поля / покрытие / качество) → следующий
        результат = запустить
        если результат true или false → записать и ОСТАНОВИТЬСЯ (валидное «нет» не ищет «да» дальше)
        если результат unknown → следующий рецепт
    ниже порога публикации → status = estimate (D18)
    ничего не сработало → status = unknown + unknown_reason; рецепт-вопрос ставит вопрос отельеру
если позже другой пригодный рецепт или отельер даёт противоречие → conflict
```

**Важно (D15).** Запасной рецепт обязан давать значение того же смысла и тех же единиц. Иначе это другая характеристика, а не следующий рецепт.

После прогона считается **покрытие**. Это материализованное представление `city_feature_coverage`, оно показывается в админке. Слоёв четыре (отчёт v2):

| Слой | Что значит |
|---|---|
| `raw_presence` | Входные данные есть |
| `license_admissible` | Входные данные разрешены лицензией |
| `computable` | Признак можно посчитать |
| `publishable` | Значение прошло проверку и публикуется |

Внутри публикуемого — доли `observed`, `computed`, `hotelier`, `unknown`.

**Знаменатель — весь каталог отелей города**, включая не привязанные к зданиям. Для полей уровня номера знаменатель — категории.

## 7. Агенты: контракты

### 7.1 Исследователь характеристик

- **Вход:** спецификация и город.
- **Инструменты:**
  - `list_recipes`;
  - `check_requirements(recipe, city)`;
  - `run_recipe(recipe, city, subjects)`;
  - `create_questions(feature, subjects)`.
- **Роль LLM:** выбрать и обосновать рецепт, когда правила неоднозначны, и описать причину низкой уверенности.
- **Без LLM** работает тот же алгоритм раздела 6. Он остаётся основным путём, поэтому система работоспособна и без ключа.

### 7.2 Агент-отельер

- **Приоритет вопроса:** сколько поисковых условий упирается в этот `unknown`, плюс конфликты и истёкшие сроки. Вопросы к одному отелю группируются в одну анкету.
- **Разбор ответа.**
  - LLM получает текст ответа и JSON-схему полей из `parse_to` спецификации. На выходе JSON, который проверяется схемой.
  - Невалидный ответ вызывает уточняющий вопрос, догадки не допускаются.
  - Ответ становится фактом `hotelier` (или `simulated_hotelier`) и сверяется с вычисленным. Расхождение создаёт `conflict`.
- **Имитатор отельера.** Отдельный модуль, отвечает по заранее заданному профилю отеля. Его ответы всегда помечены `is_simulated`.

### 7.3 Агент-поисковик

**Разбор запроса.** LLM переводит текст в AST по JSON-схеме:

```json
{
  "city": "sochi",
  "dates": {"from": "2027-07-10", "to": "2027-07-17"},
  "hard": [{"feature": "floor", "op": "lte", "value": 3}],
  "soft": [
    {"feature": "sea_view", "op": "eq", "value": true, "weight": 0.6},
    {"feature": "direct_sun_hours", "field": "midday", "op": "min", "weight": 0.4}
  ],
  "clarify": ["Даты поездки нужны для расчёта солнца"]
}
```

**Отбор** (уточнено по отчёту v3).
- Жёсткие условия уровня номера оцениваются **на размещениях категории**. Все условия запроса проверяются на **одном и том же** размещении (этаж × окна): нельзя взять «низкий этаж» у одного размещения, а «вид на море» у другого.
- Категория проходит, только если `placement_set` полный (`complete`), непустой, гарантия достаточна, а каждое допустимое размещение даёт «да». Если хоть одно «неизвестно», категория идёт в блок «надо проверить».
- Значения со статусом `estimate` в жёстких условиях не участвуют, только в мягком ранжировании и с бейджем «оценка».
- Значения `ostrovok_content` в жёстких условиях участвуют наравне с `hotelier` (D26), с бейджем «Данные Островка».
- Если у отеля есть категория со всеми «да», отель идёт в основную выдачу. Иначе — «надо проверить» с вопросом отельеру или «нет».

**Статусы для гостя (D31).** Внутренние состояния сворачиваются в три:
- **«Подходит»** — все жёсткие условия «да» на каждом допустимом размещении;
- **«Нужно уточнить»** — хотя бы одно жёсткое «неизвестно» (бывший блок «надо проверить»), рядом готовый вопрос отельеру;
- **«Не подходит»** — валидное «нет» хотя бы по одному жёсткому условию.

После имитации оформления — заголовок **«Забронировано»**. Он может стоять вместе с «по этажу нужно уточнить». Источник и дата — подписью к каждому сведению.

**Ранжирование.** `S = Σ wᵢ·uᵢ`. Неизвестное мягкое условие даёт диапазон `[0, wᵢ]`, а не ноль и не максимум.

**Объяснение.**
- LLM получает только JSON с найденными фактами и их `id`.
- Каждая цифра в тексте должна совпадать с фактом: это проверяет валидатор. Если не совпадает, показывается шаблонное объяснение.

**Уточнения по отчёту v4b** (подробно — `docs/research/review_gpt_v4b.md`):
- **AST — две схемы.** Полная локальная проверяется сервером. Компактная рабочая отправляется модели: у Claude лимит 16 union-полей, нет `oneOf` и рекурсии.
- **Жёсткие условия уровня номера:** `binding = same_placement`, `quantifier = all`.
- **Объяснения через ID утверждений.** Модель возвращает только порядок ID и связки, значения подставляет код.
- **Разбор:** сначала правила и кэш AST, LLM — для остатка. Effort задаётся явно.

**Без ключа LLM.** Явный режим «офлайн»: разбор правилами для известных шаблонов запросов, в интерфейсе стоит пометка.

### 7.4 Новая характеристика из текста

1. Текст админа попадает к LLM. Она получает реестр калькуляторов, слоёв и полей и выдаёт YAML по схеме раздела 3.
2. Валидатор проверяет, что калькуляторы и слои существуют, а единицы и уровень согласованы.
3. Спецификация сохраняется как `draft`. Пробный прогон на 20 отелях показывает покрытие, после чего админ переводит её в `active`.

## 8. Актуализация

- У каждого факта есть `expires_at` из `ttl_days` спецификации. Планировщик ставит истёкшие факты в очередь.
- Новая версия слоя (`dataset_version`) находит через `fact_dependency` зависимые факты и пересчитывает только их.
- Новый ответ отельера пересчитывает только зависящие от него факты. Пример: изменили `category_placement` — меняются обещания по категориям, но не по фасадам.
- Старые факты не удаляются: `is_current = false`, `superseded_by` указывает на новый.

## 9. Пакет города

Подтверждено отчётом v2 (D6). Пакетов два вида.

**Сборочный пакет** — вне репозитория: S3, MinIO или папка.
- Канонический и воспроизводимый: полные слои (GeoParquet, COG), граф, горизонты, сырые снимки источников.
- Используется для пересчёта.

**Рабочий пакет** — в репозитории, грузится при старте:

```
packs/sochi/
  manifest.json      # город, версия, хеши кода и спецификаций, источники
                     #   {url, release, hash, license, commercial_ok, даты}, файлы {path, bytes, rows, sha256}
  LICENSES/          # тексты лицензий и NOTICE источников
  data/*.parquet     # GeoParquet: отели, здания, фасады, факты, доказательства, покрытие
  data.dump          # опционально: pg_dump -Fc той же версии — быстрый путь загрузки
```

**Состав рабочего пакета.** В него идёт **весь каталог отелей города**, но только результаты:
- отели, их здания и фасады;
- факты с доказательствами;
- минимальная геометрия для карты.

Горизонты, граф, рельеф и полные выгрузки в рабочий пакет не идут. Размер замерим на Сочи.

**Закрытые данные** (реальные контакты отельеров, партнёрские категории) — отдельный закрытый слой, в публичный репозиторий не попадает.

**Загрузка.**
- При старте `app` сравнивает версии пакетов в `packs/` и в БД и восстанавливает недостающие через `pg_restore`. Это быстро и не требует GDAL в рантайме.

**Состав пакета.**
- В пакет кладём результаты и минимальные слои, сырые растры и полные выгрузки не кладём. Цель — десятки МБ на город.
- Источники с NC-лицензиями и с запретом распространения в пакет не попадают (поле `license_commercial_ok`).
